# Providers and constraints

Research checked 2026-09-11 against primary sources. Optional integrations must remain optional for distribution.

| Area | Baseline | Optional extension |
| --- | --- | --- |
| Chronometer | Native Time/Uptime and local Lua countdown state; no polling process | Explicit event editor and shared one-shot numeric settings editor |
| CPU | Native CPU total/per-core | UsageMonitor top processes; HWiNFO clocks/temperature/power |
| Memory Meter | Native PhysicalMemory, resident EnumPageFilesW usage/current allocation, refresh-only grouped hardware query and five UsageMonitor private-working-set ranks | Additional memory diagnostics deferred; no external provider installation |
| GPU | Scoped GPU counters and a DXCore-selected adapter metadata query at load/refresh | Existing resident host: NVIDIA temperature, framebuffer occupancy, four activity domains and current graphics clock; DXCore shared RAM and installed 64-bit NVML board power. Power/Clock default to Driver, with explicit HWiNFO overrides; metadata retains VRAM/type/maker and base/boost clocks |
| Network | One monitor combines native NetIn/NetOut, adapter/connection SysInfo and optional enabled WiFiStatus queries | Future opt-in process attribution; no separate Connection utility |
| Disk Meter | Native A–Z FreeDiskSpace type/volume-label inventory, selected-letter capacity and LogicalDisk rates; one graph for C:, selected sum, per-drive overlays or signed Split display | One-shot bundled PowerShell/CIM device-model lookup when model/both names are selected |
| Media | WebNowPlaying metadata and supported controls | Spotify Web API queue; explicit local Windows-session source detection |
| Visualizer | Built-in AudioLevel mixed output capture | Future custom process capture |

Six numeric centers use the shared helper only on an explicit click; arrows, clock/date/list choices and visibility controls use local Lua. Columns accepts 1–2, adjustment step is restricted to 1/60/300/3600 seconds, and each duration accepts 1–604800 seconds. The controller validates fixed data and captured list/slot state before saving, preserving other timers and the event. Its 88 controller checks and 25,181 native checks across three cases passed. The narrow case ran three real RunCommand/FinishAction flows with a test-only helper prelude selecting existing headless ValidateOnly/Cancel modes: 1599 saved, 604801 and cancellation preserved exact settings bytes and another running deadline, and hidden centers launched nothing. Independent final source hashes and two Settings-only captures matched, with clean logs and owned-process exit. These previews launched no countdown, provider, event editor or numeric popup; physical input, displayed-editor focus, mixed DPI and performance remain outside this evidence. See [Chronometer validation](modules/Chronometer.md#validation-record).

Network's completed main merge retains both existing native banks inside `Network/Network.ini`: two Net measures, five traffic SysInfo measures and the traffic controller update every second; eleven connection SysInfo measures update every two seconds; five validated/enabled WiFiStatus measures update every five seconds; the connection presentation controller updates every second. Economy mode preserves those intervals. Loading Network now includes the former companion's collection work, so this is not a claim of the previous traffic-only cost. No additional provider, polling process or service was introduced. The old Connection entrypoint is a no-measure, `Update=-1` compatibility redirect that activates Network and unloads itself.

Adapter-scoped metadata and traffic use `NetworkInterface`, while Wi-Fi retains its independent zero-based WLAN selection. Their displayed devices can differ; an unavailable positive native WLAN index may fall back to zero without detectable evidence. Windows' Internet report is PC-wide, and reported link rates are capacity rather than an Internet speed test. Missing/invalid adapter data and unavailable Wi-Fi stay explicit. The owner passed 27 traffic and 33 connection logic tests and 30 merged native cases with 3,390 glyph checks. Real Wi-Fi was unavailable during those captures; transfer accuracy, mixed-monitor DPI and sustained cost remain unverified. See [Network source semantics and evidence](modules/Network.md#sources-identity-and-states).

Network's completed arrow/input conversion changes no provider, query or cadence. Disk Meter implementation update, 2026-09-13: `IODriveNames=volume` uses separate native FreeDiskSpace label probes at the inventory cadence, normally 30 seconds in the monitor and only load/explicit refresh in settings. Labels can query optical/removable volume information; an empty result cannot distinguish an unnamed volume from a failed query. The current type inventory gates cached names for absent letters. Labels add no external process, but their native queries still have collection cost.

Selecting `model` or `both` enables optional RunCommand, Windows PowerShell 5.1 and local CIM lookup through bundled `DriveModels.ps1.txt`. One hidden process runs at config load, model-mode selection or explicit Refresh drives, with a 12-second timeout. Main and settings configs keep independent in-memory caches; there is no periodic model process, network request or runtime file output. The helper joins disk/partition/logical-volume associations and optionally optical names, returning bounded letter/model records without serials or device identifiers. Windows model names may describe virtual devices; network, unmapped and non-letter volumes can lack mappings. Blocked providers, failures and timeouts leave models unavailable with native labels and monitoring intact. Hotplug or letter reuse can leave a cached model stale until explicit refresh, and the Rainmeter Lua ANSI bridge may substitute unsupported characters. Every name mode uses the same letter/name-above-bar layout, with speeds and capacity sharing one line below. Name-mode changes alone do not reflow or reload the monitor or reset history. See [Disk Meter sources and constraints](modules/IO.md#telemetry-contract) and its [dependency inventory](modules/IO.md#dependencies). The helper's 34 synthetic mapping assertions, independent helper/caller review and exact-path packaging fixtures remain accepted; comparative overhead remains unmeasured.

Disk Meter's Split mode uses the same selected-drive observations and colors, displaying summed reads above zero and writes below zero with a symmetric range. The sign is presentation only and adds no counter, sample, provider or collection cadence. Missing/nonpositive current observations retain the documented zero-plot/unknown-text convention and cannot establish freshness. The final Split/control revision passed 115 Lua tests / 77,619 assertions and 328,925 source bounds checks, plus inspected default/narrow native captures without Rainmeter errors. Its four control groups add only one explicit numeric-entry path: the existing shared helper accepts 0.0001–1,000,000,000 MB/s with four decimals, then the controller validates and converts to the existing MiB/s key. Cancel, invalid output, concurrent cap changes and unchanged rounded entry preserve original saved text. The real headless process/protocol/save path passed; interactive editor and physical arrow dispatch were not established by this module run. See [Disk Meter current validation](modules/IO.md#current-validation).

GPU implementation update, 2026-09-13: the overview queries the selected adapter on this computer at load or explicit refresh. The optional NVIDIA path requires an exact DXCore LUID match and a unique physical GPU. Memory type/maker and base/boost clocks remain unknown when their interfaces are unsupported; AMD/Intel vendor-specific paths are not implemented. Missing driver support preserves available DXCore metadata. No driver or wrapper library is bundled, and no card specification is inferred from a model name. See [GPU metadata behavior](modules/GPU.md#main-discrete-gpu-information).

The existing resident GPU host now samples temperature, dedicated memory, DXCore shared memory and four NVIDIA activity domains, each with independent availability. Dedicated VRAM occupancy is physical framebuffer bytes minus currently available dedicated bytes, including driver reservations. Shared RAM displays DXCore shared-segment resident bytes and reports committed bytes separately in the tooltip; residency can exceed commitment, and neither value adds physical VRAM. The NVIDIA GPU, framebuffer/memory-controller, video and bus percentages describe independent busy time over the preceding second. They are not added, allocated memory buckets, a Task Manager D3D total or byte bandwidth; video is the combined driver domain, not separate encode/decode values. Unsupported readings show unavailable, while valid zero activity remains zero.

Temperature, memory, activity, direct power and current clock share the same one resident host, `Max(1000,MetricsInterval,SensorInterval)` sampling interval capped at 30000 ms, and three bounded temporary session paths with the existing lease and cleanup. The exact 27-field v4 snapshot retains the preceding 25 telemetry fields and appends the process-name request generation and a bounded map of PIDs to hex-encoded executable basenames. Identity, age and sequence validation remain. It adds no per-sample process, driver installation or history file. DXCore shared-memory accounting can remain available without NVIDIA interfaces; other-vendor dedicated occupancy/activity providers are not implemented. The all-adapter UsageMonitor process-engine table keeps its separate scope and independent worker cadence. See [GPU memory/activity semantics and evidence](modules/GPU.md#gpu-memory-and-driver-activity).

GPU process names are delayed display annotations from the existing host, not UsageMonitor name aggregation. Up to five unique PIDs piggyback on the existing five-second lease exchange. Limited process-query/synchronization handles and `QueryFullProcessImageNameW` resolve basenames without their final executable extension; no full path is published. Names are bounded to 128 UTF-8 bytes and validated before display. At most five handles are retained; dropped PIDs release them before replacements open, and continuously requested exited/denied/failed entries remain unavailable instead of being reopened. Missing/stale names fall back to PID without suppressing otherwise usable percentages. A name may arrive a lease interval plus a telemetry sample later. UsageMonitor supplies neither process creation identity nor counter timestamps, so the name does not prove that a retained counter belongs to the observed process lifetime. No extra host, file or polling cadence is added. Independent backend source/ABI review, helper packaging and final native/settings checks passed. See [GPU process-name semantics](modules/GPU.md#process-name-lookup).

The final GPU default and narrow runs each passed 711 settings, 139 overview, 545 graph and 2,112 telemetry assertions. Four actual typed Columns scenarios used the shared helper's unshown WinForms controls, native result callback and saved/reloaded preferences; source choices, Fit and mapping actions retained their semantics. Settled narrow captures show a Windows-resolved process basename alongside PID fallbacks, live driver values, advancing v4 sequences and one telemetry host. Stop/unload removed the owned host and three session files with zero Rainmeter errors. The helper also passed 450 backend assertions under both x64 and x86. These checks do not establish physical input, visible-editor focus, every process-name/font combination, hotplug or sustained resource cost. See [GPU final process-name/control validation](modules/GPU.md#process-names-and-settings-steppers-validation).

Direct Clock reads NVAPI's CURRENT graphics domain in kHz and displays MHz; it does not substitute memory/video clocks or load-time base/boost specifications. A present positive result is required. Direct Power uses `nvmlDeviceGetPowerUsage` from an already installed 64-bit NVML library at Windows System32 or `Program Files/NVIDIA Corporation/NVSMI`. It displays actual GPU-and-associated-circuitry consumption in watts: instantaneous on GA100 and older architectures, one-second average on Ampere except GA100 and newer architectures. Valid zero power remains zero; watts are not estimated from TDP or utilization. The provider requires complete NVAPI/NVML inventories and a unique PCI association to the exact DXCore/NVAPI-selected card, retaining PCI domain, rejecting nonzero functions and checking identity before and after the read. Missing/ambiguous mappings, unsupported APIs or absent libraries leave power unavailable. A 32-bit host reports direct power Unsupported while other supported readings continue. No NVML binary or SDK is bundled, and no `nvidia-smi` process is launched. [NVIDIA power semantics](https://docs.nvidia.com/deploy/nvml-api/api/group__nvmlDeviceQueries.html) and [clock selectors/domains](https://docs.nvidia.com/nvapi/group__gpuclock.html) define those readings.

`GPUPowerSource` and `GPUClockSource` default independently to literal `0` (Driver); literal `1` explicitly selects HWiNFO. There is no automatic fallback in either direction, and switching sources preserves the saved export mappings. All nine Registry measures start disabled. A four-measure override bank enables only when its source and `GPUEnableSensors` are both literal `1`; the shared name-enumeration measure enables only when at least one bank is needed. Enabled export reads round SensorInterval up to skin updates, while HWiNFO controls its own acquisition cadence and export age remains unknown. Provider/source controls stay accessible during failures. The owner verified x64/x86 lifecycle behavior, 1,514 native telemetry assertions, 432 settings assertions and inspected narrow/default captures; independent source/ABI review found no blocker in the final helper. The later Lua RunCommand cleanup correction passed two isolated native checks: explicit Stop and an injected lease-write failure each stopped the owned host within four seconds while GPU remained loaded, before its minimum 15-second lease expiry; both removed session files without Rainmeter errors. Other hardware, mixed DPI, non-ASCII temp paths and comparative overhead remain unverified. See [GPU direct power/clock behavior and evidence](modules/GPU.md#direct-gpu-power-and-current-clock).

Memory Meter implementation update: one local `Win32_PhysicalMemory` inventory query supplies manufacturer, exact module capacity, raw type and configured rate for the grouped overview. A documented manufacturer-only fallback may inspect a part-family pattern transiently; part numbers are not emitted or saved. Native PhysicalMemory still supplies physical RAM used/total. PAGE now uses Windows `EnumPageFilesW` to sum `TotalInUse` and `TotalSize` page counts across all paging files, multiplying by the OS page size. It reports actual paging-file usage/current allocated capacity, excluding RAM and system commit accounting. The denominator can grow with allocation and is not the configured maximum; the old SwapMemory measures are removed. The independent PAGE bar shows the validated used/allocated ratio without changing physical-RAM history or its separate bar.

The bundled `PageFileHost.cs.txt` source runs through existing RunCommand, Windows PowerShell and .NET: one bootstrap plus one resident host, with no dependency installation or per-sample process. Sampling follows `MetricsInterval` clamped to 1–30 seconds. Up to 512 ASCII snapshot bytes carry aggregate values/status, token, sequence and time through three temporary `.dat`/`.tmp`/`.lease` siblings with atomic publication and a bounded lease. Paging-file names and paths are not read or emitted. Complete successful enumeration with no files shows No paging file; zero use with positive capacity stays valid. Unsupported APIs, partial/error results, malformed/stale frames and stopped-host states remain explicit. Lease expiry and the retained Rainmeter ancestor handle bound host lifetime; the corrected Lua controller stops only tracked, freshly checked running-status-`0` commands. A standalone resident-host lease/cleanup probe passed, as did source/ABI review and provider tests. The exact helper staging allowance and packaging fixtures passed without executing the helper. Final controls and independent bars passed 97,497 source assertions across 438 configurations and 28,283 assertions in six native fixture cases. Those cases launched no PAGE, inventory, UsageMonitor or numeric-input process; actual popup delivery, Rainmeter unload/ancestor-exit integration and resource cost remain unverified. See [RAM provider semantics](modules/RAM.md#live-memory-semantics-and-units) and [scoped validation](modules/RAM.md#validation-results).

Memory Meter's process ranks retain `Alias=RAM` / `Working Set - Private`, aggregate same-name instances, and share the Process category's one-second worker independently of skin cadence. They cannot be summed as system-wide RAM/PAGE usage or treated as PID-level records. Unit/precision changes reformat cached RAM/PAGE, inventory and process data without new telemetry work. Separate `RAMShowBar`, `RAMShowPageBar` and `RAMShowHistory` choices affect presentation only; setup failures do not overwrite them.

RAM's completed settings controls add no collection work. Units wrap between GB/MB; two precision fields clamp to integers 0–2, and their typed centers launch the existing shared helper only on explicit entry. The three visibility controls remain toggles. The controller validates bounded data before a per-key save; cached reformatting does not refresh RAM, rerun inventory or reset history. Module tests use mocked typed responses, with the shared helper's native evidence recorded separately by integration.

[UsageMonitor](https://github.com/rainmeter/rainmeter-docs/blob/master/source/manual/plugins/usagemonitor.html) polls categories once per second independently of skin cadence and shares workers. Its GPU aggregate is not automatically a 0-100% whole-adapter metric; Task Manager uses the [busiest engine](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/). Process I/O includes network/device/file activity and must not be called disk throughput; use disk counters for that purpose.

[HWiNFO registry/Gadget exports](https://github.com/rainmeter/rainmeter-docs/blob/master/source/tips/hwinfo.html) can be read by Rainmeter without a separate plugin or Shared Memory. Map sensor labels as well as indices. The non-Pro shared-memory interface has a 12-hour limit; Pro removes that limit. Check current [licensing](https://www.hwinfo.com/licenses/) and redistribution rights before release. Minimize sensor polling, particularly EC/SMI/SMART sources with documented [latency issues](https://hwinfo.com/forum/threads/known-issues.398/).

[WebNowPlaying](https://wnp.keifufu.dev/rainmeter/usage) provides metadata/buttons and supports [desktop players](https://wnp.keifufu.dev/desktop-players), including Spotify Desktop without Spicetify. Not every player supports every command. Its documented interface does not expose Spotify's queue.

Parallax's optional source observer identifies Spotify when one observed Windows session matches WNP's title, artist and playback state. Ambiguous or stale results retain the generic Windows label. Explicit Start enables it, and subsequent normal Player loads can resume it from private saved intent. It samples every two seconds and keeps bounded metadata in private local runtime storage; it uses no Spotify credentials, network request or playback action. Stop controls only this observer and disables recovery. It remains separate from the authenticated queue provider. See [Media's source detection contract](modules/Media.md#optional-spotify-source-detection) for lifecycle, expiry and correlation limits.

Media recovery runs once per load through a bundled Lua include, only when Rainmeter's settings path is the normal `%APPDATA%\Rainmeter` profile. Player considers both Source and Queue; Setup and standalone Queue consider only Queue; Settings and isolated/custom profiles resume neither. Each provider requires exact valid enabled intent and no Stop marker. Source Start and queue Start/Restart/successful Connect enable recovery; Stop disables it, as do queue Disconnect/Configure. Older installations require Start once: tokens and snapshots alone do not opt in. Resume never opens authentication or clears Stop; the queue worker retains saved authorization and existing Retry-After/quota gates. Control and worker mutexes serialize lifecycle actions; Queue also rejects obsolete launch permits. Interactive Connect can still delay or time out Stop, as documented in the [recovery contract](modules/Media.md#provider-recovery-after-restart). Closing a view leaves enabled workers running, and no OS startup task, service or repeated process launcher is introduced.

Media's completed numeric controls change no provider lifecycle: Columns 1–2, queue rows 1–5 and queue polling 30–150 use integer steps of one, with one shared helper launch only for explicit typed entry. The interval retains its restart reminder. A fresh ready snapshot confirming zero queue items now requests the existing inline-collapse callback once per empty transition, persists `QueueExpanded=0` and refreshes Media/open settings. Missing, expired, malformed, error and setup states do not imply empty; later items do not re-expand it, and the standalone Queue panel is unchanged. Focused evidence includes 3,684 native settings assertions, 284 rendered-collapse assertions and 2,378 queue-reader assertions across 24 injected cases, with source agreement and inspected captures. These tests made no Spotify request; module settings tests used an inert input proxy, with shared helper checks recorded separately. See [Media validation](modules/Media.md#validation-report).

Spotify exposes a [queue endpoint](https://developer.spotify.com/documentation/web-api/reference/get-queue). A native helper should use [PKCE](https://developer.spotify.com/documentation/web-api/tutorials/code-pkce-flow), explicit loopback [redirects](https://developer.spotify.com/documentation/web-api/concepts/redirect_uri), minimal scopes and protected per-user storage. Honor [rate limits](https://developer.spotify.com/documentation/web-api/concepts/rate-limits). Current [quota rules](https://developer.spotify.com/documentation/web-api/concepts/quota-modes) require Premium for development app owners and allow only five allowlisted users. Extended quota applications have organizational eligibility requirements. Public distribution cannot assume a shared client ID works for all users; user-supplied application setup is an advanced option. Spotify-connected features need a release policy review, including restrictions on synchronizing recordings with visual media.

[AudioLevel](https://github.com/rainmeter/rainmeter-docs/blob/master/source/manual/plugins/audiolevel.html) analyzes device audio. Use one parent FFT, a bounded number of bands and a standalone skin. The visualizer is a generic audio spectrum display, not an audio equalization DSP or a guarantee of Spotify-only capture.

Visualizer's fourth palette interpolates Accent 1 through Accent 2, including alpha, across the existing 24 FFT bands. `Color.lua` applies colors only on refresh, without file access or an Update callback; no capture or telemetry work is added. Audio Settings remains static and starts neither AudioLevel nor Win7Audio collection. Its nine controls include five numeric and four categorical fields; only explicit numeric entry launches the shared one-shot helper. The controller uses loaded variables, so its validation is not a concurrent external-file edit or post-write verification guarantee. Final source checks cover 37 choices, 45 action targets and 40 geometries; 179 native-Lua cases use mocked controller calls. Four separate actual helper cases passed the RunCommand/WinForms/result/save path with programmatic child-window events, including rejecting a height outside the three supported presets. Three main/settings captures were inspected with clean logs. Physical input, popup rendering, mixed DPI, audio accuracy and performance remain unverified; see [Visualizer validation](modules/Visualizer.md#gradient-native-check).
