# CPU Meter

CPU owns `Skins/Parallax/CPU/`, `@Resources/Modules/CPU/`, `@Resources/User/CPU.inc` and this report. The main entrypoint is `Parallax\CPU\CPU.ini`; its independent settings utility is `Parallax\CPU\Settings\Settings.ini`. Both follow the shared appearance and geometry contract. The user-provided title CPU icon and table-header Zap, Flame and Gauge artwork are from Lucide Icons v1.8.0 under the ISC license; licensed SVG source geometry, rendered PNGs and the required notice are in `@Resources/Modules/CPU/Icons/`. All other code and gear artwork are original; no ModernGadgets assets or binaries were copied.

## Display

The hover-only gear replaces the total usage number while the pointer is over the painted meter. Clicking it opens CPU Settings in its own movable window. The four sections are:

- **Processor Info:** Windows processor model, then a single line `n-cores (x-threads) @ Base (Turbo) GHz`, where n is the true/physical core count and x is the logical processor/thread count. For this machine the summary is `6-cores (12-threads) @ 3.20 (4.60) GHz`. The parenthetical is an optional configured advertised turbo limit, never a live clock reading. A compact Current clock row follows the panel and uses only HWiNFO's CPU-wide `Core Clocks` export; it is not a base-clock, turbo-limit, per-core, or per-thread substitute. It shows `Unavailable` when that exact export cannot be safely read. The selected font size is retained; long summaries clip within the panel and keep their full details on hover. There are no separate count labels, "Processor Info" heading or "Processor Name:" label. Measured values are detected; configured limits are explicitly identified.
- **CPU Table:** one **Thread / high-voltage Zap / Flame / Gauge** table, with numeric thread labels 1 through the detected count. Each row keeps its own native Windows utilization and right-aligned bar within the Thread column. At the user's request, adjacent thread pairs share a core's HWiNFO sensors: threads 1/2 use Core 0, 3/4 use Core 1, through 11/12 using Core 5 on this machine. At their defaults, voltage rows show requested VID to three decimals as `1.234V`, and temperature rows show whole Celsius degrees as `65°C`; CPU Settings can change those independent precisions. Values keep no spaces before their units. Tooltips explain the pairing and voltage meaning. Borders separate headers and footers. Missing individual exports stay dashed in both paired rows; CPU-wide values never fill these cells. The optional footer shows selected CPU-wide temperature/voltage, explicitly labeled Avg for Core Temperatures and VID for requested voltage.
- **Top Process List:** matching Process and Gauge table columns with header/bottom rules. The Gauge and percentages share the centerline of a 42-logical-pixel utilization field. Process rows contain names and percentages without bars, leaving more room for names. Ranked CPU use comes from Rainmeter's bundled UsageMonitor, excluding Idle and _Total. Same-name process instances are grouped. The table displays up to the selected number of names with paired percentages, highest usage first; full names remain available in tooltips when clipped.
- **Graph:** the Settings source control chooses either the total-CPU trace or an overlay of every logical-thread trace. Both modes use the same bounded 62-logical-pixel graph, shared 0–100% vertical scale, and shared time axis. Per-thread collection uses each active Windows logical processor's absolute identity, independently of Thread-table paging. Each trace shares its selected thread color with that thread's utilization bar. There is no graph label or legend. Newest observations are at the right; uncollected history remains blank.

The panel lays out visible sections in order and collapses hidden sections. Automatic rows show every validated logical processor on one page, up to 64. Sensor availability does not change the table height. Missing or sparse HWiNFO core identities never renumber or compact the thread pairs. Manual paging uses each row's absolute thread number for its sensor pairing. The processor panel is 34 logical pixels high, with the model and one summary line; the 16-pixel current-clock row follows it with an 8-pixel gap. The minimum total height is 80 logical pixels.

The Thread bar uses the right side of its column and the shared Data Bar Thickness setting (1–12 logical pixels). `#DataBarThicknessPx#` resolves it to `Max(1, Round(DataBarThickness × Scale))` physical pixels, retaining a visible one-pixel bar at 75% scale. It is centered vertically in its 16-pixel row, so even the maximum setting clears adjacent rows at every supported suite scale. Voltage, temperature and utilization reserve 44, 34 and 42 logical pixels respectively. Temperature values are right-aligned, and utilization values are centered below the Gauge in their 42-pixel field; the eight logical pixel gap after temperature lengthens the Thread bar. The Zap, Flame and Gauge header images occupy centered 14-logical-pixel bounds over their respective data fields. White Lucide source artwork is recolored at draw time through Greyscale and ImageTint, following WarningColor, CPUColor and HeaderTextColor. Names retain full explanatory tooltips. The CPU identity icon scales with TitleFontSize, and it, the title, live total and hover gear share the vertical title row. Titles inherit TitleFontSize/TitleTextColor, headings use HeaderFontSize/HeaderTextColor, and readings use FontSize/TextColor without shrinking. The live total is body text. Table header rules use TableHeaderBorderColor/TableHeaderBorderThickness; footer and section dividers use DividerColor/DividerThickness. The adaptive outer panel honors BorderThickness and background alpha. Graph styling remains independent.

## CPU Settings

The independent settings utility uses the shared Global Settings layout: labels remain on the panel, only value fields are shaded, and rows use 28 logical pixel pitch. Appearance, Processes, History, Performance and HWiNFO setup headings use HeaderFontSize with Accent 1; values use body FontSize/TextColor. Its close control aligns with the title center. The shared note retains its direct Global Settings link. Settings always uses two columns, with a content-derived height from 888 to 1000 logical pixels; these local dimensions never overwrite the main meter's saved Columns or PanelHeight.

Seven numeric controls use shared previous/value/next styles and the one-shot `Scripts/SettingsInput.ps1` UtilityNumber editor. Process count accepts integers 1–10; history capacity 10–300; percentage and temperature decimals 0–1; voltage decimals 0–3; CPU refresh 500–2000 milliseconds; and sensor reads 500–5000 milliseconds. Arrow steps are one for counts/precision, ten samples for history capacity and 500 milliseconds for rates. Arrows clamp, become inactive at limits and perform no boundary write or refresh. Typed entry accepts every integer in the supported range, including custom values between the old presets. Enter applies; Esc cancels. The module validates the fixed key allowlist, response protocol, integer range, completed RunCommand status and unchanged pending value again before saving. No user text becomes a command. Closing settings terminates only its pending, still-running numeric input.

History source and Search scope have wrapping previous/next choices; clicking their centers advances the choice. A Search scope change retains the existing identity reset and scan behavior. Show switches and sensor enablement remain toggles. Named Temperature/Voltage export pickers, Scan, Open HWiNFO, the official guide, reconnect and Thread Colors retain their command/provider semantics. Thread Colors still opens the CPU-only bounded hex/swatch editor; color edits apply to both the matching thread bar and graph trace.

Process count collapses when the process list is hidden (28 pixels), and History source/capacity collapse when history is hidden (56 pixels). Thread Colors collapses only when neither the thread table nor a visible per-thread graph uses it (28 pixels). Every hidden component has zero X-independent Y/W/H bounds and no native hit area; later sections and physical window bounds reflow. All Show controls, section headings and setup/recovery remain accessible. Percentage precision still affects the always-visible total, and voltage/temperature precision still affects the always-visible sensor footer, so those formatting controls remain. Provider availability or enablement does not collapse setup. Values survive hide/show, refresh and reopening.

HWiNFO setup preserves its enable switch, Open HWiNFO, official guide, four setup steps, Scan sensors, last-scan diagnostics, named CPU-wide Temperature/Voltage selectors, automatic Core Clocks discovery, Search scope and reconnect. There are no global appearance controls in this utility. The shared-settings context action remains available.

Settings save immediately to `@Resources/User/CPU.inc`. A click sends a variable only to the main skin's `ParallaxCPU` group, then updates its dedicated event-only apply measure. That measure invokes the controller's preference handler without updating table CPU measures or adding a history sample. Show/hide and thread-color edits therefore apply immediately, without refreshing CPU or pressing Apply. Processor metadata survives changes. Changing graph visibility, source or capacity intentionally clears its buffer; changing a color redraws preserved history. Per-thread mode enables its dedicated absolute-thread CPU measures only while the graph is visible, waits for two native interval updates, and disables them again in total mode. Re-enabling the CPU table waits for fresh native interval samples.

CPU refresh accepts 500–2000 integer milliseconds, and HWiNFO reads accept 500–5000 integer milliseconds. A rate value is saved immediately and refreshes CPU Meter only because Rainmeter applies its skin update cadence and Registry measure dividers on load; this intentionally restarts the CPU history. The HWiNFO value tooltip explains that its effective rate rounds up to the next CPU refresh, so a 500 ms target with a 2 s CPU refresh reads every 2 s. The process ranking provider remains independently collected at about 1 Hz; a 500 ms CPU refresh can redraw its most recent available ranking but does not create a faster UsageMonitor worker.

The settings utility itself uses `Update=-1`; no polling is needed. Opening it starts one read-only scan. Scan sensors and reconnect explicitly scan again and reconnect a loaded CPU meter. It can close independently or save preferences while CPU is unloaded. The main meter reads those preferences on its next load. Existing saved visibility selections are retained. Opening the settings window reflects the current CPU user file.

## Data sources and limitations

CPU model is read once from the native Registry measure at `HKEY_LOCAL_MACHINE\HARDWARE\DESCRIPTION\System\CentralProcessor\0\ProcessorNameString`. The display removes trademark markers and nominal-clock suffixes; the full string is available on hover. Physical/logical totals use one hidden Windows PowerShell CIM query of `Win32_Processor` at load/refresh through bundled RunCommand, with a 10-second timeout. It writes no output file and does not run on polling updates. Pending, failed or malformed results show Checking/Unavailable. HWiNFO is not needed for these fields. [Registry](https://docs.rainmeter.net/manual/measures/registry/), [RunCommand](https://docs.rainmeter.net/manual/plugins/runcommand/), [Win32_Processor](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-processor)

The combined second line extracts nominal CPU base frequency only from an explicit terminal `@ <number>GHz` or MHz suffix in that existing processor model string; MHz converts to GHz. The i7-8700's reported 3.20 GHz matches Intel's base-frequency specification. `CPUTurboClock` is a separately configured advertised turbo limit in explicit MHz or GHz; it only appears when it is valid and higher than the detected base clock. The current user profile sets it to the i7-8700's advertised 4.60 GHz maximum turbo frequency. No extra query or polling is added. A missing/malformed base suffix displays `Unavailable`, and missing topology displays `?-cores (?-threads)`. Current speed, WMI `MaxClockSpeed`, and HWiNFO `Core Clocks` are not turbo-limit fallbacks. Counts cover the exposed Windows processor packages; clock/name identify the primary processor. Tooltips explain the notation and source. [Intel i7-8700 specifications](https://www.intel.com/content/www/us/en/products/sku/126686/intel-core-i78700-processor-12m-cache-up-to-4-60-ghz/specifications.html), [Win32_Processor MaxClockSpeed](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-processor)

Native usage uses Rainmeter CPU measures at CPU Meter's selected refresh cadence, initially 1000 ms. Overall startup data is discarded; newly enabled core slots wait for a priming update and an interval sample. The 64 page-relative table measures start disabled at safe Processor=0, and only validated visible indices are enabled. A separate set of 64 fixed absolute-thread measures remains disabled unless the visible graph source is Per thread, so table-page changes cannot corrupt a trace's history. The Windows NUMBER_OF_PROCESSORS environment value must be an integer 1–64. Missing/invalid counts disable core slots; greater than 64 reports unsupported. Processor groups, altered environment values, affinity constraints, hot-added CPUs and VM topology remain limitations. [CPU measure](https://docs.rainmeter.net/manual/measures/cpu/)

UsageMonitor uses Alias=CPU, so process values are percentages of total CPU. Rollup=1 groups same-name instances; entries are not PID-specific. A ranked index with zero activity returns an empty name, which is not displayed as a named zero reading. Empty rankings show Waiting or No active process data. Its API supplies no independent freshness/error signal, so empty/stale counters cannot reliably be distinguished from inactivity. Process percentages and native total usage can differ because collection times and providers differ. [UsageMonitor](https://docs.rainmeter.net/manual/plugins/usagemonitor/)

UsageMonitor's Process category worker collects independently at about 1 Hz. Hiding the list disables its display measures, but does not claim to stop that shared worker. Unload the CPU skin, and any other skins using that category, to remove its collection cost. No repeated subprocess polling, external plugin installation or binary download is required. Steady-state overhead has not been measured.

The 60-sample graph has 59 intervals between full-buffer endpoints, about 59 seconds at the default 1-second CPU refresh. The selected refresh rate changes that span. Scheduling delays and suspend/resume can stretch this; the graph is a sample sequence rather than a timestamped axis. A known-invalid total reading clears the total trace; a known-invalid per-thread reading clears only that trace. The per-thread renderer retains every selected observation and draws at most one point per horizontal pixel for each overlaid trace. Each trace is rendered as its own colored path so overlapping threads remain distinguishable; default colors repeat after twelve threads until edited. Native counters can otherwise retain stale values without an error flag, so freshness cannot be guaranteed.

## HWiNFO setup and sensor meaning

Open CPU Settings and use the HWiNFO Setup section. **Open HWiNFO** launches the standard installation under Program Files only when clicked; a portable/custom installation produces instructions to open it manually. **Setup guide** opens Rainmeter's official instructions. Neither action installs software or enables exports automatically.

In HWiNFO64 Sensors, open the configuration gear and **HWiNFO Gadget**. Enable **Enable reporting to Gadget**, then select **Report value in Gadget** for the primary CPU's exact **Core Clocks** item, each **Core N** temperature in the CPU DTS group, and each **Core N VID** in the primary CPU group. **Distance to TjMAX** is not a temperature. For optional CPU-wide summary values, also report CPU Package or Core Temperatures and measured Vcore/VR VOUT/CPU Core Voltage, or Core VIDs. Click **OK**, then **Scan sensors** in CPU Settings. HWiNFO must remain running. The adapter does not enable exports automatically or use a shared-memory plugin. [Official setup guide](https://github.com/rainmeter/rainmeter-docs/blob/master/source/tips/hwinfo.html)

**Scan sensors** shows HWiNFO's running state and which supported CPU exports were found, with a specific missing-export instruction. Results are labeled **Last scan**, not live telemetry. Individual core sensors are discovered automatically. CPU-wide T and CPU-wide V cycle through Auto and named summary readings; changes save immediately and reconnect CPU Meter. No numeric-index entry is needed. **Search scope** cycles Automatic, Current user and All users; changing scope resets both sensor choices to Auto because indices belong to that scope. Mirrored identical candidates are deduplicated; conflicting identities at the same index are excluded until a specific scope is chosen. Unavailable/empty candidates never become fabricated readings or saved zero indices. Up to 128 validated candidates are listed per scan.

Per-core discovery accepts exact Core N temperatures under the primary CPU DTS group and exact Core N VID voltage labels under CPU [#0], for N=0–63. The separate current-clock row accepts only the exact primary-CPU `Core Clocks` export in MHz or GHz; it rejects individual, effective and bus clocks. It rejects GPU/other-package sensors, Distance to TjMAX, invalid units and ambiguous duplicate identities. CPU-wide temperature accepts CPU Package or CPU (Tctl/Tdie), preferring those over the Core Temperatures average fallback. Measured CPU-wide Vcore is preferred to aggregate VID. Explicit summary selections still require supported labels/units. A vanished manual selection can reset to Auto. No machine-specific export indices are distributed as defaults.

Vcore is measured CPU supply voltage; VID is requested voltage. The V column's tooltips explicitly identify VID, and the summary retains the VID label. Core Temperatures is the current arithmetic mean of the core temperatures, so its summary reads Avg rather than Package. The user's two-thread pairing is an explicit presentation mapping, `HWiNFO core = floor((thread - 1) / 2)`. A prior read-only Windows topology probe confirmed adjacent sibling pairs on this i7-8700. This is not a general topology discovery mechanism: other CPUs, disabled SMT or reordered logical processors may require a different mapping. It does not equate Windows CoreIndex with HWiNFO IDs, and no topology query was added to production. [HWiNFO VID explanation](https://www.hwinfo.com/forum/threads/can-i-view-actual-cpu-core-voltages-not-vids.8586/), [HWiNFO average temperature explanation](https://www.hwinfo.com/forum/threads/nonsense-min-and-max-cpu-core-temperature-values-on-system-tray-icons.7182/page-3)

`DiscoverSensors.ps1` runs once on refresh, sensor re-enable, Reconnect or an observed HWiNFO64 stopped-to-running transition through bundled RunCommand, with a 10-second timeout. It reads only native 64-bit `SOFTWARE\HWiNFO64\VSB` values; it does not write files/registry, download anything or start other processes. Its ASCII protocol hex-encodes sensor identities as data. Native Registry measures subsequently read Sensor, Label, Value and ValueRaw at CPU Meter's selected HWiNFO target (initially 2 seconds), rounded up to the CPU refresh cadence. A native Process measure suppresses retained registry values when HWiNFO64 exits and triggers one fresh discovery when that process returns. Only discovered fields and their hive's value-name list are enabled. Sensor polling launches no subprocesses.

Main discovery adds `-CoreList`; both that mode and setup `-List` emit up to 128 validated `CORE` records with provider core ID, kind, hive, export index and identity. There is no inferred Windows mapping. Setup uses the same helper with optional `-List`, which adds supported candidate identities and a read-only HWiNFO64 process check. Bounded request IDs correlate each result with its scan; stale/late results cannot replace a newer request. Native CPU discovery also correlates requests, queues the latest changed mapping if a previous discovery is still running, and preserves a provider-restart retry until the in-flight callback finishes. Timeouts are bounded; setup's timeout is a single delayed action, not a recurring update. No file/registry writes occur during scanning; preferences are written only when the user changes a selection.

The child Windows PowerShell process uses `-ExecutionPolicy RemoteSigned` for this locally authored helper. It does not persist an execution-policy change; Group Policy and download-origin restrictions still apply. A blocked helper reports unavailable rather than changing machine policy or unblocking files. Initial native testing exposed Windows PowerShell 5.1's default script restriction even though the development PowerShell runtime had a different policy. [Microsoft execution-policy scopes](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-5.1)

Every reading must still match its discovered sensor/label identity, required registry fields and recognized units. Fahrenheit and millivolts convert to Celsius and volts; GHz converts to MHz before the current-clock row is formatted. Temperature unit parsing accepts both UTF-8 and the ANSI degree byte returned by the native Rainmeter Lua bridge. Missing fields, changed identities/units, invalid numbers and values outside the supported temperature/voltage/clock bounds show a dash or `Unavailable` for the clock row. Reconnect clears bindings first. Failed or timed-out discovery remains unavailable. The registry protocol exposes no sample timestamp: paused sensors or stale exports while HWiNFO is still running cannot be reliably detected. Tooltips state that sample age is unknown. Changing CPU Meter's HWiNFO read target does not change HWiNFO's own polling or overhead. Registry exports avoid the shared-memory timeout; licensing and redistribution still follow the suite provider contract. [Registry measure](https://docs.rainmeter.net/manual/measures/registry/), [Process measure](https://docs.rainmeter.net/manual/measures/process/), [HWiNFO licensing](https://www.hwinfo.com/licenses/)

## Implementation

- `CPU/CPU.ini`: header, processor info, graph, table styles and independent settings action.
- `CPU/Settings/Settings.ini`: separate event-driven settings config.
- `CPU/Colors/Colors.ini`, `Modules/CPU/ThreadColors.lua`, `ThreadColorInput.ps1` and `ThreadColorMeters.inc`: CPU-only bounded hex/swatch editor and immediate color bridge for logical threads 1–64.
- `Modules/CPU/CPU.lua`: adaptive section layout, core binding, process presentation, individually colored history paths and preference application.
- `Modules/CPU/Measures.inc`: 129 native CPU measures (one total, 64 page-relative table slots and 64 absolute graph slots), two metadata measures, 10 UsageMonitor measures, an event-only apply measure and one controller.
- `Modules/CPU/SensorMeasures.inc`, `Sensors.lua`, `DiscoverSensors.ps1`: 18 optional sensor/discovery/event measures, including four identity-checked CPU-wide Core Clocks fields, validated native-read presentation, and one-shot read-only discovery.
- `Modules/CPU/CoreMeters.inc`: 64 bounded thread slots with usage, paired voltage/temperature, and table borders.
- `Modules/CPU/CoreSensorMeasures.inc`: 512 initially disabled native Registry fields; only discovered sensor fields become active. The former separate CoreSensorMeters include is removed.
- `Modules/CPU/ProcessMeters.inc`: process heading/state and 10 bounded name/value slots.
- `Modules/CPU/Settings.lua`, `SettingsMeters.inc` and the shared `Scripts/SettingsInput.ps1`: CPU-only display controls, conditional settings layout, bounded numeric steppers/typed entry, wrapping enums, guided sensor setup, bounded named selection, persistence and immediate event delivery.
- `Modules/CPU/tests/validate_cpu.py`: developer-only source/startup geometry validation; Python is not a runtime dependency.
- `Modules/CPU/tests/Test-DiscoverSensors.ps1`, `validate_sensors.lua` and `validate_sensor_setup.lua`: offline protocol/selection and controller/setup behavior tests. These fixtures are excluded from distribution.

Settings events use documented SetVariableGroup and UpdateMeasureGroup bangs. An earlier implementation used an invalid CommandMeasureGroup bang; native integration exposed it and the final sender replaces it. Evidence must check each Rainmeter launch's log before a later launch replaces the log. [Bangs](https://docs.rainmeter.net/manual/bangs/)
