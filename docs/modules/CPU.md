# CPU Meter

CPU owns `Skins/Parallax/CPU/`, `@Resources/Modules/CPU/`, `@Resources/User/CPU.inc` and this report. The main entrypoint is `Parallax\CPU\CPU.ini`; its independent settings utility is `Parallax\CPU\Settings\Settings.ini`. Both follow the shared appearance and geometry contract. All code and chip/gear artwork are original; no ModernGadgets assets or binaries were copied.

## Display

The hover-only gear replaces the total usage number while the pointer is over the painted meter. Clicking it opens CPU Settings in its own movable window. The four sections are:

- **Processor Info:** Windows processor model, then `n-cores (x-threads) @ Base Clock`, where n is the true/physical core count and x is the logical processor/thread count. For this machine the detected summary is `6-cores (12-threads) @ 3.20 GHz`. At narrow widths or larger body text, the clock moves to the next line; the selected font size is retained. There are no separate count labels, "Processor Info" heading or "Processor Name:" label. Values are detected, not shipped telemetry.
- **CPU Table:** Core, V, T and % columns, without a separate CPU Table/range heading or Native status line. A utilization bar sits to the right of the logical-processor label inside the Core column. Rules separate the column headers and close the table below its data rows. LP labels identify logical processors, including hardware threads, rather than physical-core identities. Optional HWiNFO exports supply CPU-wide voltage and package temperature in Celsius. Those shared readings repeat across LP rows; they are not individual thread sensors. The voltage header changes to VID when the export is requested voltage. Missing readings display a dash, never a fabricated zero.
- **Top Process List:** matching Process and % table columns, header/bottom rules, and right-aligned red utilization bars inside the Process column. Ranked CPU use comes from Rainmeter's bundled UsageMonitor, excluding Idle and _Total. Same-name process instances are grouped. The table displays up to the selected number of names with paired percentages, highest usage first; full names remain available in tooltips when clipped.
- **Graph:** a bounded history of actual overall CPU samples, with a 0–100% scale and newest values at the right. Uncollected history remains blank.

The panel lays out visible sections in order and collapses hidden sections. Automatic rows show every validated logical processor on one page, up to 64. The processor panel is 34 logical pixels high when its summary fits one line and 50 when the clock wraps. On this 12-LP machine, all four sections with five process entries occupy a 494- or 510-pixel painted height (502 or 518 including gutters at scale 1). The main header and total remain available when sections are hidden. The minimum height is 80 logical pixels.

The Core bar uses the right side of its column; the remaining fixed-width columns reserve 32 logical pixels each for V and T and 52 for utilization. This preserves space for a percentage with one decimal place at supported widths and body sizes. Names clip within their cells and retain explanatory/full-name tooltips. Titles inherit TitleFontSize/TitleTextColor, table/process/settings headings use HeaderFontSize/HeaderTextColor, and readings/other text use FontSize/TextColor. The live total is body text. Setup guide uses AccentColor2; primary actions retain AccentColor. Table/process rules use DividerColor/DividerThickness, and the adaptive outer panel honors BorderThickness and BackgroundColor including alpha. Graph grids and metric colors retain their own roles.

## CPU Settings

The settings utility uses two columns and a 716-pixel logical height. It has four corresponding groups, each with a Show section switch. CPU Table also has percentage precision; Top Process List has process-count presets 3, 5 and 10; Graph has history-capacity presets 30, 60, 120 and 300. Its HWiNFO Setup section adds the enable switch, Open HWiNFO, an official setup-guide link, four setup steps, Scan sensors, last-scan diagnostics, named Temperature/Voltage selectors, Search scope, and reconnect. There are no global appearance controls in this utility. The shared-settings context action remains available as required by the suite contract.

Settings save immediately to `@Resources/User/CPU.inc`. A click sends a variable only to the main skin's `ParallaxCPU` group, then updates its dedicated event-only apply measure. That measure invokes the controller's preference handler without updating native CPU measures or adding a history sample. Show/hide therefore applies immediately, without refreshing CPU or pressing Apply. Processor metadata survives changes. Changing history visibility or capacity intentionally clears its buffer. Re-enabling the CPU table waits for fresh native interval samples.

The settings utility itself uses `Update=-1`; no polling is needed. Opening it starts one read-only scan. Scan sensors and reconnect explicitly scan again and reconnect a loaded CPU meter. It can close independently or save preferences while CPU is unloaded. The main meter reads those preferences on its next load. Existing saved visibility selections are retained. Opening the settings window reflects the current CPU user file.

Supported CPU variables:

| Key | Meaning |
| --- | --- |
| `Columns` | Main meter width, 1 or 2. Settings has its own two-column layout. |
| `PanelHeight` | Minimum logical height, initially 80. Runtime height grows with visible sections and does not overwrite this preference. |
| `CPUAutoRows` | 1 shows all validated logical processors without paging. |
| `CPUCoresPerPage` | Advanced manual page size 1–64, used only when CPUAutoRows=0; fallback 8. |
| `CPUPage` | Saved manual page, clamped to available pages. Paging controls appear only when needed. |
| `CPUCoreLimit` | 0 uses detected count; positive values can only reduce it. |
| `CPUShowInfo`, `CPUShowCores`, `CPUShowProcesses`, `CPUShowHistory` | Individual section visibility: 0 hides, 1 shows. |
| `CPUProcessCount` | 1–10 ranked process names; fallback 5. |
| `CPUHistorySamples` | 10–300 observed samples; fallback 60. |
| `CPUDecimals` | 0 or 1 decimal place for CPU percentages. |
| `CPUSensorsEnabled` | 1 reads optional HWiNFO Gadget exports; 0 suppresses readings and disables native sensor measures immediately. |
| `CPUSensorHive` | Auto checks the native 64-bit HKCU and HKLM export keys; HKCU or HKLM explicitly selects one. |
| `CPUTemperatureIndex`, `CPUVoltageIndex` | -1 automatically chooses a uniquely identified export; 0–4096 explicitly selects a supported exported index. These still require matching CPU labels and units. |

Missing/invalid display choices use bounded fallbacks in memory. Preferences are written only on user actions. History, collected process names, topology and startup state are not persisted. Manual file edits require refreshing the affected utilities. Packager variable preservation must include `Parallax\@Resources\User\CPU.inc`.

## Data sources and limitations

CPU model is read once from the native Registry measure at `HKEY_LOCAL_MACHINE\HARDWARE\DESCRIPTION\System\CentralProcessor\0\ProcessorNameString`. The display removes trademark markers and nominal-clock suffixes; the full string is available on hover. Physical/logical totals use one hidden Windows PowerShell CIM query of `Win32_Processor` at load/refresh through bundled RunCommand, with a 10-second timeout. It writes no output file and does not run on polling updates. Pending, failed or malformed results show Checking/Unavailable. HWiNFO is not needed for these fields. [Registry](https://docs.rainmeter.net/manual/measures/registry/), [RunCommand](https://docs.rainmeter.net/manual/plugins/runcommand/), [Win32_Processor](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-processor)

The combined second line extracts nominal CPU base frequency only from an explicit terminal `@ <number>GHz` or MHz suffix in that existing processor model string; MHz converts to GHz. The i7-8700's reported 3.20 GHz matches Intel's base-frequency specification. No extra query or polling is added. A missing/malformed suffix displays `Unavailable`, and missing topology displays `?-cores (?-threads)`. Current speed and maximum/turbo speed are not base-frequency fallbacks. Counts cover the exposed Windows processor packages; clock/name identify the primary processor. Tooltips explain the notation and source. [Intel i7-8700 specifications](https://www.intel.com/content/www/us/en/products/sku/126686/intel-core-i78700-processor-12m-cache-up-to-4-60-ghz/specifications.html)

Native usage uses Rainmeter CPU measures and the shared MetricsInterval, initially 1000 ms. Overall startup data is discarded; newly enabled core slots wait for a priming update and an interval sample. All 64 core measures start disabled at safe Processor=0, and only validated indices are enabled. The Windows NUMBER_OF_PROCESSORS environment value must be an integer 1–64. Missing/invalid counts disable core slots; greater than 64 reports unsupported. Processor groups, altered environment values, affinity constraints, hot-added CPUs and VM topology remain limitations. [CPU measure](https://docs.rainmeter.net/manual/measures/cpu/)

UsageMonitor uses Alias=CPU, so process values are percentages of total CPU. Rollup=1 groups same-name instances; entries are not PID-specific. A ranked index with zero activity returns an empty name, which is not displayed as a named zero reading. Empty rankings show Waiting or No active process data. Its API supplies no independent freshness/error signal, so empty/stale counters cannot reliably be distinguished from inactivity. Process percentages and native total usage can differ because collection times and providers differ. [UsageMonitor](https://docs.rainmeter.net/manual/plugins/usagemonitor/)

UsageMonitor's Process category worker collects independently at about 1 Hz. Hiding the list disables its display measures, but does not claim to stop that shared worker. Unload the CPU skin, and any other skins using that category, to remove its collection cost. No repeated subprocess polling, external plugin installation or binary download is required. Steady-state overhead has not been measured.

The 60-sample graph has 59 intervals between full-buffer endpoints, about 59 seconds at a 1-second update. Scheduling delays and suspend/resume can stretch this; the graph is a sample sequence rather than a timestamped axis. Known-invalid total readings clear history. Native counters can otherwise retain stale values without an error flag, so freshness cannot be guaranteed.

## HWiNFO setup and sensor meaning

Open CPU Settings and use the HWiNFO Setup section. **Open HWiNFO** launches the standard installation under Program Files only when clicked; a portable/custom installation produces instructions to open it manually. **Setup guide** opens Rainmeter's official instructions. Neither action installs software or enables exports automatically.

In HWiNFO64 Sensors, open the configuration gear and the **HWiNFO Gadget** tab. Enable **Enable reporting to Gadget**, then select **Report value in Gadget** separately for CPU Package temperature and a CPU voltage reading. A measured **Vcore**, **VR VOUT** or **CPU Core Voltage** is preferred; **Core VIDs** under CPU [#0] is a supported fallback. Click **OK** to save in HWiNFO, return to CPU Settings and click **Scan sensors**. HWiNFO must remain running. No HWiNFO shared-memory plugin is used, and the adapter does not change HWiNFO configuration. [Rainmeter HWiNFO setup](https://github.com/rainmeter/rainmeter-docs/blob/master/source/tips/hwinfo.html)

**Scan sensors** shows HWiNFO's running state and which supported CPU exports were found, with a specific missing-export instruction. Results are labeled **Last scan**, not live telemetry. Click Temperature or Voltage to cycle Auto and the detected sensor names; changes save immediately and reconnect CPU Meter. No numeric-index entry is needed. **Search scope** cycles Automatic, Current user and All users; changing scope resets both sensor choices to Auto because indices belong to that scope. Mirrored identical candidates are deduplicated; conflicting identities at the same index are excluded until a specific scope is chosen. Unavailable/empty candidates never become fabricated readings or saved zero indices. Up to 128 validated candidates are listed per scan.

Temperature discovery accepts CPU Package or AMD CPU (Tctl/Tdie) under CPU [#0]. Voltage discovery rejects GPU and additional CPU package groups and accepts the exact supported labels above. Multiple distinct candidates stay unavailable until a named sensor/search scope is chosen. Identical mirrored HKCU/HKLM mappings are deduplicated. A vanished manually selected export can always be reset to Auto, including when no candidates remain. Custom labels outside this supported set are unavailable, even with an explicit index. No machine-specific indices or labels are saved in distribution.

Vcore is supplied CPU voltage; VID is requested voltage and must not be presented as an actual per-core supply measurement. The current adapter intentionally reads one shared voltage and one package temperature, repeated in the logical-processor table with a CPU-wide footer and explanatory header/cell tooltips. Windows logical-processor numbering is not assumed to map to HWiNFO physical-core indices. Per-physical-core temperatures remain a future mapping feature. [HWiNFO voltage explanation](https://www.hwinfo.com/forum/threads/can-i-view-actual-cpu-core-voltages-not-vids.8586/)

`DiscoverSensors.ps1` runs once on refresh, sensor re-enable or Reconnect through bundled RunCommand, with a 10-second timeout. It reads only native 64-bit `SOFTWARE\HWiNFO64\VSB` values; it does not write files/registry, download anything or start other processes. Its ASCII protocol hex-encodes sensor identities as data. Native Registry measures subsequently read Sensor, Label, Value and ValueRaw at the shared SensorInterval (initially 2 seconds). A native Process measure suppresses retained registry values when HWiNFO64 exits. Only discovered fields and their hive's value-name list are enabled. Sensor polling launches no subprocesses.

Setup uses the same helper with optional `-List`, which adds supported candidate identities and a read-only HWiNFO64 process check. Bounded request IDs correlate each result with its scan; stale/late results cannot replace a newer request. Native CPU discovery also correlates requests and queues the latest changed mapping if a previous discovery is still running. Timeouts are bounded; setup's timeout is a single delayed action, not a recurring update. No file/registry writes occur during scanning; preferences are written only when the user changes a selection.

The child Windows PowerShell process uses `-ExecutionPolicy RemoteSigned` for this locally authored helper. It does not persist an execution-policy change; Group Policy and download-origin restrictions still apply. A blocked helper reports unavailable rather than changing machine policy or unblocking files. Initial native testing exposed Windows PowerShell 5.1's default script restriction even though the development PowerShell runtime had a different policy. [Microsoft execution-policy scopes](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-5.1)

Every reading must still match its discovered sensor/label identity, required registry fields and recognized units. Fahrenheit and millivolts convert to Celsius and volts. Missing fields, changed identities/units, invalid numbers and values outside the supported temperature/voltage bounds show a dash. Reconnect clears bindings first. Failed or timed-out discovery remains unavailable. The registry protocol exposes no sample timestamp: paused sensors or stale exports while HWiNFO is still running cannot be reliably detected. Tooltips state that sample age is unknown. Changing Parallax's SensorInterval does not change HWiNFO's own polling or overhead. Registry exports avoid the shared-memory timeout; licensing and redistribution still follow the suite provider contract. [Registry measure](https://docs.rainmeter.net/manual/measures/registry/), [Process measure](https://docs.rainmeter.net/manual/measures/process/), [HWiNFO licensing](https://www.hwinfo.com/licenses/)

## Implementation

- `CPU/CPU.ini`: header, processor info, graph, table styles and independent settings action.
- `CPU/Settings/Settings.ini`: separate event-driven settings config.
- `Modules/CPU/CPU.lua`: adaptive section layout, core binding, process presentation, history and preference application.
- `Modules/CPU/Measures.inc`: 65 native CPU measures, two metadata measures, 10 UsageMonitor measures, an event-only apply measure and one controller.
- `Modules/CPU/SensorMeasures.inc`, `Sensors.lua`, `DiscoverSensors.ps1`: 14 optional sensor/discovery/event measures, validated native-read presentation, and one-shot read-only discovery.
- `Modules/CPU/CoreMeters.inc`: 64 bounded table slots plus column headers and borders.
- `Modules/CPU/ProcessMeters.inc`: process heading/state and 10 bounded name/value slots.
- `Modules/CPU/Settings.lua` and `SettingsMeters.inc`: CPU-only display controls, guided sensor setup, bounded named selection, persistence and immediate event delivery.
- `Modules/CPU/tests/validate_cpu.py`: developer-only source/startup geometry validation; Python is not a runtime dependency.
- `Modules/CPU/tests/Test-DiscoverSensors.ps1`, `validate_sensors.lua` and `validate_sensor_setup.lua`: offline protocol/selection and controller/setup behavior tests. These fixtures are excluded from distribution.

Settings events use documented SetVariableGroup and UpdateMeasureGroup bangs. An earlier implementation used an invalid CommandMeasureGroup bang; native integration exposed it and the final sender replaces it. Evidence must check each Rainmeter launch's log before a later launch replaces the log. [Bangs](https://docs.rainmeter.net/manual/bangs/)
