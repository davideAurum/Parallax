# CPU Meter

CPU owns `Skins/Parallax/CPU/`, `@Resources/Modules/CPU/`, `@Resources/User/CPU.inc` and this report. The main entrypoint is `Parallax\CPU\CPU.ini`; its independent settings utility is `Parallax\CPU\Settings\Settings.ini`. Both follow the shared appearance and geometry contract. The user-provided title CPU icon and table-header Zap, Flame and Gauge artwork are from Lucide Icons v1.8.0 under the ISC license; licensed SVG source geometry, rendered PNGs and the required notice are in `@Resources/Modules/CPU/Icons/`. All other code and gear artwork are original; no ModernGadgets assets or binaries were copied.

## Display

The hover-only gear replaces the total busy-time number while the pointer is over the painted meter. Clicking it opens CPU Settings in its own movable window. The four sections are:

- **Processor Info:** Windows processor model, then a single line `n-cores (x-threads) @ Base (Turbo) GHz`, where n is the true/physical core count and x is the logical processor/thread count. For this machine the summary is `6-cores (12-threads) @ 3.20 (4.60) GHz`. The parenthetical is an optional configured advertised turbo limit, never a live clock reading. Compact Clock, Fan and MB Fan rows follow the panel. Clock prefers HWiNFO's CPU-wide `Core Clocks` export and otherwise derives an aggregate Windows clock from `Processor Frequency × % Processor Performance`; neither source is a base-clock, turbo-limit, per-core, or per-thread substitute. The two are different measurements, so a Windows reading is always marked `Windows` in muted text at the row's right edge, and an HWiNFO reading carries no mark. The fan rows accept validated HWiNFO Gadget RPM exports whose exact labels identify the CPU and motherboard fans; they have no native Windows fallback and show `Unavailable` when absent. The selected font size is retained; long summaries clip within the panel. There are no separate count labels, "Processor Info" heading or "Processor Name:" label. Measured values are detected; configured limits are explicitly identified.
- **CPU Table:** one **Thread / high-voltage Zap / Flame / Gauge** table, with numeric thread labels 1 through the detected count. Each row shows Windows % Processor Time, the share of time that logical processor was busy (0–100%), and keeps its right-aligned bar within the Thread column; the bar and the number share one 0–100% scale. Thread N is Windows logical processor N−1, which Task Manager labels CPU N−1. At the user's request, adjacent thread pairs share a core's HWiNFO sensors: threads 1/2 use Core 0, 3/4 use Core 1, through 11/12 using Core 5 on this machine. At their defaults, voltage rows show requested VID to three decimals as `1.234V`, and temperature rows show whole Celsius degrees as `65°C`; CPU Settings can change those independent precisions. Values keep no spaces before their units. Borders separate headers and footers. Missing individual exports stay dashed in both paired rows; CPU-wide values never fill these cells. The footer line under the graph shows HWiNFO status only: `HWiNFO sensors: off`, `HWiNFO: connecting...`, `HWiNFO: not running`, `HWiNFO: open Sensors` (the export is not updating; see [HWiNFO export durability](#hwinfo-export-durability-2026-10-23)), `HWiNFO: Gadget exports unavailable`, `HWiNFO: no per-core exports`, `HWiNFO: core readings unavailable`, or `HWiNFO: connected, N cores` (N counts cores with a per-core reading).
- **Top Process List:** matching Process and Gauge table columns with header/bottom rules. The Gauge and percentages share the centerline of the Thread table's 50-logical-pixel busy-time field. Process rows contain names and percentages without bars, leaving more room for names. Ranked CPU use comes from Rainmeter's bundled UsageMonitor, excluding Idle and _Total. Same-name process instances are grouped. The table displays up to the selected number of names with paired percentages, highest usage first.
- **Graph:** the Settings source control chooses either the total busy-time trace or an overlay of every logical-thread busy-time trace. Both modes use the same bounded 62-logical-pixel graph, shared 0–100% vertical scale, and shared time axis. Valid samples are 0–100%, so drawn traces and the numeric readings use the same values. Per-thread collection uses each active Windows logical processor's absolute identity, independently of Thread-table paging. Each trace shares its selected thread color with that thread's Thread bar. There is no graph label or legend. Newest observations are at the right; uncollected history remains blank.

The panel lays out visible sections in order and collapses hidden sections. Automatic rows show every validated logical processor on one page, up to 64. Sensor availability does not change the table height. Missing or sparse HWiNFO core identities never renumber or compact the thread pairs. Manual paging uses each row's absolute thread number for its sensor pairing. The processor panel is 34 logical pixels high, with the model and one summary line; 16-pixel Clock, Fan and MB Fan rows follow it, then an 8-pixel gap. Either fan row collapses independently. The minimum total height is 80 logical pixels.

The Thread bar uses the right side of its column and the shared Data Bar Thickness setting (1–12 logical pixels). `#DataBarThicknessPx#` resolves it to `Max(1, Round(DataBarThickness × Scale))` physical pixels, retaining a visible one-pixel bar at 75% scale. It is centered vertically in its 16-pixel row, so even the maximum setting clears adjacent rows at every supported suite scale. Voltage, temperature and busy time reserve 44, 34 and 50 logical pixels respectively. Temperature values are right-aligned, and busy-time values are centered below the Gauge in their 50-pixel field, which holds `100.0%` at the 10 pt body maximum; the eight logical pixel gap after temperature lengthens the Thread bar. The Zap, Flame and Gauge header images occupy centered 14-logical-pixel bounds over their respective data fields. White Lucide source artwork is recolored at draw time through Greyscale and ImageTint, following WarningColor, CPUColor and HeaderTextColor. The CPU identity icon scales with TitleFontSize, and it, the title, live total and hover gear share the vertical title row. Titles inherit TitleFontSize/TitleTextColor, headings use HeaderFontSize/HeaderTextColor, and readings use FontSize/TextColor without shrinking. The live total is body text. Table header rules use TableHeaderBorderColor/TableHeaderBorderThickness; footer and section dividers use DividerColor/DividerThickness. The adaptive outer panel honors BorderThickness and background alpha. Graph styling remains independent.

## CPU Settings

The independent settings utility uses the shared Global Settings layout: labels remain on the panel, only value fields are shaded, and rows use 28 logical pixel pitch. Appearance, Processes, History, Performance and HWiNFO setup headings use HeaderFontSize with Accent 1; values use body FontSize/TextColor. Its close control aligns with the title center. The shared note retains its direct Global Settings link. Settings always uses two columns, with a content-derived height from 944 to 1056 logical pixels; these local dimensions never overwrite the main meter's saved Columns or PanelHeight.

Seven numeric controls use shared previous/value/next styles and the one-shot `Scripts/SettingsInput.ps1` UtilityNumber editor. Process count accepts integers 1–10; history capacity 10–300; percentage and temperature decimals 0–1; voltage decimals 0–3; CPU refresh 500–2000 milliseconds; and sensor reads 500–5000 milliseconds. Arrow steps are one for counts/precision, ten samples for history capacity and 500 milliseconds for rates. Arrows clamp, become inactive at limits and perform no boundary write or refresh. Typed entry accepts every integer in the supported range, including custom values between the old presets. Enter applies; Esc cancels. The module validates the fixed key allowlist, response protocol, integer range, completed RunCommand status and unchanged pending value again before saving. No user text becomes a command. Closing settings terminates only its pending, still-running numeric input.

History source and Search scope have wrapping previous/next choices; clicking their centers advances the choice. A Search scope change retains the existing identity reset and scan behavior. Show switches and sensor enablement remain toggles. Named Temperature/Voltage export pickers, Scan, Open HWiNFO, the official guide, reconnect and Thread Colors retain their command/provider semantics. Thread Colors still opens the CPU-only bounded hex/swatch editor; color edits apply to both the matching thread bar and graph trace.

Process count collapses when the process list is hidden (28 pixels), and History source/capacity collapse when history is hidden (56 pixels). Thread Colors collapses only when neither the thread table nor a visible per-thread graph uses it (28 pixels). Every hidden component has zero X-independent Y/W/H bounds and no native hit area; later sections and physical window bounds reflow. All Show controls, section headings and setup/recovery remain accessible. Percentage precision still affects the always-visible total, and voltage/temperature precision still affects the Thread table's V/T cells, so those formatting controls remain. Provider availability or enablement does not collapse setup. Values survive hide/show, refresh and reopening.

HWiNFO setup preserves its enable switch, Open HWiNFO, official guide, four setup steps, Scan sensors, last-scan diagnostics, named CPU-wide Temperature/Voltage selectors, automatic Core Clocks and fan discovery, Search scope and reconnect. There are no global appearance controls in this utility. The shared-settings context action remains available.

Settings save immediately to `@Resources/User/CPU.inc`. A click sends a variable only to the main skin's `ParallaxCPU` group, then updates its dedicated event-only apply measure. That measure invokes the controller's preference handler without updating table utility measures or adding a history sample. Show/hide and thread-color edits therefore apply immediately, without refreshing CPU or pressing Apply. Processor metadata survives changes. Changing graph visibility, source or capacity intentionally clears its buffer; changing a color redraws preserved history. Per-thread mode enables its dedicated absolute-thread % Processor Time measures only while the graph is visible, waits for two interval updates, and disables them again in total mode. Re-enabling the CPU table waits for fresh interval samples.

CPU refresh accepts 500–2000 integer milliseconds, and HWiNFO reads accept 500–5000 integer milliseconds. A rate value is saved immediately and refreshes CPU Meter only because Rainmeter applies its skin update cadence and Registry measure dividers on load; this intentionally restarts the CPU history. The effective HWiNFO read rate rounds up to the next CPU refresh, so a 500 ms target with a 2 s CPU refresh reads every 2 s. UsageMonitor collects every category it serves, including the Processor Information busy-time and clock counters and the process ranking, on its own fixed one-second timer. A 500 ms CPU refresh therefore redraws each sample about twice, and a 2000 ms refresh shows about every other one-second sample rather than a two-second average; the refresh rate never changes the measurement window.

The settings utility itself uses `Update=-1`; no polling is needed. Opening it starts one read-only scan. Scan sensors and reconnect explicitly scan again and reconnect a loaded CPU meter. It can close independently or save preferences while CPU is unloaded. The main meter reads those preferences on its next load. Existing saved visibility selections are retained. Opening the settings window reflects the current CPU user file.

## Data sources and limitations

CPU model is read once from the native Registry measure at `HKEY_LOCAL_MACHINE\HARDWARE\DESCRIPTION\System\CentralProcessor\0\ProcessorNameString`. The display removes trademark markers and nominal-clock suffixes. Physical/logical totals use one hidden Windows PowerShell CIM query of `Win32_Processor` at load/refresh through bundled RunCommand, with a 10-second timeout. It writes no output file and does not run on polling updates. Pending, failed or malformed results show Checking/Unavailable. HWiNFO is not needed for these fields. [Registry](https://docs.rainmeter.net/manual/measures/registry/), [RunCommand](https://docs.rainmeter.net/manual/plugins/runcommand/), [Win32_Processor](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-processor)

The combined second line extracts nominal CPU base frequency only from an explicit terminal `@ <number>GHz` or MHz suffix in that existing processor model string; MHz converts to GHz. The i7-8700's reported 3.20 GHz matches Intel's base-frequency specification. `CPUTurboClock` is a separately configured advertised turbo limit in explicit MHz or GHz; it only appears when it is valid and higher than the detected base clock. The current user profile sets it to the i7-8700's advertised 4.60 GHz maximum turbo frequency. No extra query or polling is added. A missing/malformed base suffix displays `Unavailable`, and missing topology displays `?-cores (?-threads)`. Current speed, WMI `MaxClockSpeed`, and HWiNFO `Core Clocks` are not turbo-limit fallbacks. Counts cover the exposed Windows processor packages; clock/name identify the primary processor. [Intel i7-8700 specifications](https://www.intel.com/content/www/us/en/products/sku/126686/intel-core-i78700-processor-12m-cache-up-to-4-60-ghz/specifications.html), [Win32_Processor MaxClockSpeed](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-processor)

Total and per-thread load use Rainmeter's bundled UsageMonitor against Windows `Processor Information\\% Processor Time`. This is busy time: the share of each sample a logical processor spent running non-idle work, and for `_Total` the average across logical processors, 0–100. It is not adjusted for clock speed; the Clock row reports turbo separately. UsageMonitor 1.0.1 collects the whole category on its own hard-coded 1000 ms timer, independent of `CPUUpdateInterval`, and each reading is the change between its last two collections. Values outside 0–100.5 are rejected and valid values clamp to 100, so the header, Thread rows, bars and graph share one 0–100 scale; the 0.5 allowance only absorbs single-precision rounding at full load. UsageMonitor reports a missing or not-yet-warmed instance as 0, which is indistinguishable from an idle reading. The total instance is `_Total`; logical processors use Windows group/thread names `0,0` through `0,63`. Overall startup data is discarded; newly enabled table slots wait for a priming update and an interval sample. The 64 page-relative table measures start disabled at safe `Name=0,0`, and only validated visible indices are enabled. A separate set of 64 fixed absolute-thread measures remains disabled unless the visible graph source is Per thread, so table-page changes cannot corrupt a trace's history. The Windows NUMBER_OF_PROCESSORS environment value must be an integer 1–64. Missing/invalid counts disable thread slots; greater than 64 reports unsupported. Additional processor groups, altered environment values, affinity constraints, hot-added CPUs and VM topology remain limitations. [UsageMonitor](https://docs.rainmeter.net/manual/plugins/usagemonitor/), [Task Manager standard metrics, KB5064081](https://support.microsoft.com/en-us/topic/august-29-2025-kb5064081-os-build-26100-5074-preview-3f9eb9e1-72ca-4b42-af97-39aace788d93), [Microsoft time versus utility counters](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/cpu-usage-exceeds-100)

The process list uses UsageMonitor with Alias=CPU, so process values are time-based percentages of total CPU. Rollup=1 groups same-name instances; entries are not PID-specific. A ranked index with zero activity returns an empty name, which is not displayed as a named zero reading. Empty rankings show Waiting or No active process data. Its API supplies no independent freshness/error signal, so empty/stale counters cannot reliably be distinguished from inactivity. Process percentages and the total now share a time basis, but the rows still need not add up to the total: the list shows only the top entries, the Process and Processor Information categories run on separate one-second UsageMonitor timers, and each process is normalized by the Process `_Total` instance, which includes Idle. When a process with accumulated CPU time exits, the Process `_Total` change collapses for one collection and the remaining rows inflate for about a second; a replica of UsageMonitor's calculation showed a steady 8.4% process reading 68.0%. That plugin behavior has not yet been observed in the live skin. [UsageMonitor](https://docs.rainmeter.net/manual/plugins/usagemonitor/)

UsageMonitor's Process category worker collects independently at about 1 Hz, process-wide, while any loaded measure in any skin names the category; a `Disabled=1` measure still keeps it registered. Since 2026-10-23 the ten process slots load only while the list is shown: `Measures.inc` includes `ProcessMeasures<CPUShowProcesses>.inc`, and `ProcessMeasures0.inc` is comment-only. With the list hidden CPU Meter therefore keeps no Process reader alive; Memory Meter's own process measures still do while it is loaded, which is expected sharing (one reader serves both). See [UsageMonitor registration by include](#usagemonitor-registration-by-include-2026-10-23). No repeated subprocess polling, external plugin installation or binary download is required. Steady-state overhead has not been measured.

The 60-sample graph has 59 intervals between full-buffer endpoints, about 59 seconds at the default 1-second CPU refresh. The selected refresh rate changes that span. Scheduling delays and suspend/resume can stretch this; the graph is a sample sequence rather than a timestamped axis. A known-invalid total reading clears the total trace; a known-invalid per-thread reading clears only that trace. The per-thread renderer retains every selected observation and draws at most one point per horizontal pixel for each overlaid trace. Each trace is rendered as its own colored path so overlapping threads remain distinguishable; default colors repeat after twelve threads until edited. Native counters can otherwise retain stale values without an error flag, so freshness cannot be guaranteed.

## HWiNFO setup and sensor meaning

Open CPU Settings and use the HWiNFO Setup section. **Open HWiNFO** launches the standard installation under Program Files only when clicked; a portable/custom installation produces instructions to open it manually. **Setup guide** opens Rainmeter's official instructions. Neither action installs software or enables exports automatically.

In HWiNFO64 main settings, enable **Remember Preferences**. In Sensors, open the configuration gear and **HWiNFO Gadget**. Enable **Enable reporting to Gadget**, then select **Report value in Gadget** for each **Core N** temperature in the CPU DTS group, each **Core N VID** in the primary CPU group, the RPM reading named **CPU** or **CPU Fan**, and the RPM reading named **Mainboard** or **Motherboard**. **Core Clocks** is optional because the clock row has a native Windows fallback. **Distance to TjMAX** is not a temperature. For optional CPU-wide summary values, also report CPU Package or Core Temperatures and measured Vcore/VR VOUT/CPU Core Voltage, or Core VIDs. Click **OK**, then use **Quit & Save** once so HWiNFO persists the choices before relying on autorun. Reopen HWiNFO and select **Scan sensors** in CPU Settings. HWiNFO must remain running with its **Sensors** window open; minimised is fine. HWiNFO polls its sensors, and writes the Gadget export, only while that window is open, so an HWiNFO that autostarts to the tray without it leaves the export frozen. HWiNFO's own settings can show Sensors at startup; that choice is the user's and Parallax does not change it. The adapter does not enable exports automatically or use a shared-memory plugin. [Official setup guide](https://github.com/rainmeter/rainmeter-docs/blob/master/source/tips/hwinfo.html)

**Scan sensors** shows HWiNFO's running state and which supported CPU exports were found, with a specific missing-export instruction. Results are labeled **Last scan**, not live telemetry. Individual core sensors are discovered automatically. CPU-wide T and CPU-wide V cycle through Auto and named summary readings; changes save immediately and reconnect CPU Meter. No numeric-index entry is needed. **Search scope** cycles Automatic, Current user and All users; changing scope resets both sensor choices to Auto because indices belong to that scope. Mirrored identical candidates are deduplicated; conflicting identities at the same index are excluded until a specific scope is chosen. Unavailable/empty candidates never become fabricated readings or saved zero indices. Up to 128 validated candidates are listed per scan. Runtime telemetry is mapped directly from each validated Gadget index to native Rainmeter Registry measures; the one-shot scan only resolves and verifies those mappings.

Per-core discovery accepts exact Core N temperatures under the primary CPU DTS group and exact Core N VID voltage labels under CPU [#0], for N=0–63. The separate current-clock row accepts only the exact primary-CPU `Core Clocks` export in MHz or GHz; it rejects individual, effective and bus clocks. Fan discovery accepts RPM readings with the exact label CPU, CPU Fan, CPU Fan Speed or CPU Fan 1 outside GPU and secondary-CPU groups. Multiple distinct matches remain unavailable instead of choosing one arbitrarily. Discovery rejects GPU/other-package sensors, Distance to TjMAX, invalid units and ambiguous duplicate identities. CPU-wide temperature accepts CPU Package or CPU (Tctl/Tdie), preferring those over the Core Temperatures average fallback. Measured CPU-wide Vcore is preferred to aggregate VID. Explicit summary selections still require supported labels/units. A vanished manual selection can reset to Auto. No machine-specific export indices are distributed as defaults.

Vcore is measured CPU supply voltage; VID is requested voltage. The V column shows only per-core VID, CPU Settings notes that VID is requested voltage, and the summary retains the VID label. Core Temperatures is the current arithmetic mean of the core temperatures, so its summary reads Avg rather than Package. The user's two-thread pairing is an explicit presentation mapping, `HWiNFO core = floor((thread - 1) / 2)`. A prior read-only Windows topology probe confirmed adjacent sibling pairs on this i7-8700. This is not a general topology discovery mechanism: other CPUs, disabled SMT or reordered logical processors may require a different mapping. It does not equate Windows CoreIndex with HWiNFO IDs, and no topology query was added to production. [HWiNFO VID explanation](https://www.hwinfo.com/forum/threads/can-i-view-actual-cpu-core-voltages-not-vids.8586/), [HWiNFO average temperature explanation](https://www.hwinfo.com/forum/threads/nonsense-min-and-max-cpu-core-temperature-values-on-system-tray-icons.7182/page-3)

`DiscoverSensors.ps1` runs once on refresh, sensor re-enable, Reconnect or an observed HWiNFO64 stopped-to-running transition through bundled RunCommand, with a 10-second timeout. It reads only native 64-bit `SOFTWARE\HWiNFO64\VSB` values; it does not write files/registry, download anything or start other processes. Its ASCII protocol hex-encodes sensor identities as data. Native Registry measures subsequently read Sensor, Label, Value and ValueRaw at CPU Meter's selected HWiNFO target (initially 2 seconds), rounded up to the CPU refresh cadence. A native Process measure suppresses retained registry values when HWiNFO64 exits and triggers one fresh discovery when that process returns. Only discovered fields and their hive's value-name list are enabled. Sensor polling launches no subprocesses.

Main discovery adds `-CoreList`; both that mode and setup `-List` emit up to 128 validated `CORE` records with provider core ID, kind, hive, export index and identity. There is no inferred Windows mapping. Setup uses the same helper with optional `-List`, which adds supported candidate identities and a read-only HWiNFO64 process check. Bounded request IDs correlate each result with its scan; stale/late results cannot replace a newer request. Native CPU discovery also correlates requests, queues the latest changed mapping if a previous discovery is still running, and preserves a provider-restart retry until the in-flight callback finishes. Timeouts are bounded; setup's timeout is a single delayed action, not a recurring update. No file/registry writes occur during scanning; preferences are written only when the user changes a selection.

The child Windows PowerShell process uses `-ExecutionPolicy RemoteSigned` for this locally authored helper. It does not persist an execution-policy change; Group Policy and download-origin restrictions still apply. A blocked helper reports unavailable rather than changing machine policy or unblocking files. Initial native testing exposed Windows PowerShell 5.1's default script restriction even though the development PowerShell runtime had a different policy. [Microsoft execution-policy scopes](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-5.1)

Every HWiNFO reading must still match its discovered sensor/label identity, required registry fields and recognized units. Fahrenheit and millivolts convert to Celsius and volts; GHz converts to MHz before the current-clock row is formatted. Temperature unit parsing accepts both UTF-8 and the ANSI degree byte returned by the native Rainmeter Lua bridge. Missing fields, changed identities/units, invalid numbers and values outside the supported temperature/voltage bounds show a dash. A missing, unsupported or frozen HWiNFO clock, a stopped or connecting HWiNFO and sensors turned off all fall back to the Windows aggregate clock, marked `Windows`; `Unavailable` appears only if that also fails. Reconnect clears HWiNFO bindings first. Failed or timed-out discovery remains unavailable for temperature and voltage. The Gadget registry protocol exposes no sample timestamp. CPU Meter therefore treats the export as not updating when every bound raw value has stayed the same for 60 seconds while HWiNFO runs. Bound values are all the per-core temperatures and VIDs, Core Clocks, both fans and the CPU-wide summaries. It then shows `HWiNFO: open Sensors`, which names the usual fix, and suppresses the readings, as it does for a stopped HWiNFO; the first changed value restores them. This is a heuristic with known limits. A frozen export still shows as connected for up to a minute after load, reconnect or a restart. A system whose only bound readings are a few coarse values that hold perfectly still for a minute could be flagged until one moves. An HWiNFO polling period of 60 seconds or longer would trip it too. Changing CPU Meter's HWiNFO read target does not change HWiNFO's own polling or overhead. Registry exports avoid the shared-memory timeout; licensing and redistribution still follow the suite provider contract. [Registry measure](https://docs.rainmeter.net/manual/measures/registry/), [Process measure](https://docs.rainmeter.net/manual/measures/process/), [HWiNFO licensing](https://www.hwinfo.com/licenses/)

## Frozen HWiNFO export (2026-10-22)

The [performance review](../PERFORMANCE-REVIEW.md#found-along-the-way-not-performance) found that HWiNFO's registry export on this PC stopped updating on 2026-10-01 while HWiNFO kept running. CPU Meter went on showing those three-week-old VIDs, temperatures, clock and fan speeds as `HWiNFO: connected`, which breaks the rule that stale data is never shown as live. This is a separate commit, and the owner may drop it.

- **What changed.** `Sensors.lua` builds one signature from the raw value of every bound export. When the signature has not changed for 60 seconds while HWiNFO runs, the footer reads `HWiNFO: export not updating`.
  - The V/T cells show dashes and both fans show `Unavailable`.
  - Clock falls back to the live Windows aggregate, as it does when HWiNFO is stopped.
  - Any change in any bound value restores the readings at once.
  - Turning sensors off, reconnecting, or a stopped or restarted HWiNFO starts a fresh 60-second window.
  - It adds no process, timer or registry access; it reuses the values the Registry measures already read.
- **Why every value together.** A single reading can legitimately hold still, such as an idle core's whole-degree temperature or a fixed fan. Requiring all bound values to freeze together, VIDs and Core Clocks included, keeps one constant reading from flagging a live export.
- **Tests.** `tests/validate_sensors.lua` passes 66 cases under OBS's LuaJIT. Three new cases fail on the previous code:
  - an export frozen for 60 s is reported, with readings suppressed and the native clock shown, and stays reported until a value changes;
  - constant readings beside one that changes every 48 s stay live;
  - a stopped provider takes precedence, and a restart or reconnect restarts the window.
  - A fourth case confirms that no frozen state appears without bound exports.
- **Native check.** HWiNFO was running, and none of its 47 exported raw values changed before or during the run. A 75-second capture of the isolated CPU skin showed `HWiNFO: export not updating`, dashed V/T cells, `Unavailable` fans and a live Windows clock of 3.87 GHz in place of the frozen 4.28 GHz. The log had no errors.
  - The capture came from a fixture copy of this source. Only that copy's `Preview-Parallax.ps1` settle limit was raised to 90 s, and the CPU files were hash-checked identical.
  - Evidence: `build/cpu-stale-preview-source-853d736e183c/build/Parallax-visual-preview-20261023T020616730Z-a23dc1cd/captures/CPU.png`.
- **Not verified:** recovery against a live HWiNFO whose export resumes; it is covered only offline. The live skin was not touched.

## Performance hygiene (2026-10-22)

This is package A3 of step 2 in the [performance review](../PERFORMANCE-REVIEW.md), covering findings CPU-01 to CPU-04, XMOD-04 and ENGINE-05. Each change is its own commit, so each can be measured or reverted alone. None is meant to change what the skin shows.

- **One repaint per tick (CPU-01, XMOD-04).** `CPU.lua`'s `Update()` and `Sensors.lua`'s periodic `render()` no longer end with `!UpdateMeterGroup CPUUI` and `!Redraw`.
  - Both bangs ran synchronously inside the measure loop. Each tick forced an extra pass over about 368 meters and painted the window two or three times, about 2.5 paints a second.
  - The skin now paints once per tick, after its own meter pass. That pass applies everything the scripts set, because every meter they change per tick has `UpdateDivider` 1.
  - Settings changes, paging, discovery results, reconnects and the deferred processor details still repaint immediately.
- **No per-tick plugin reloads (CPU-02, ENGINE-05).** The 64 table slots and 10 process slots no longer have `DynamicVariables=1`.

  - A Reload that lands while UsageMonitor's worker holds its lock starts a thread.
  - `CPU.lua` now sends a slot's `Name`, and its enable or disable, only when that value changes. Each `!SetOption` still forces the one re-read the slot needs.
- **Change-gated bangs (CPU-04).**
  - `set()` and `visible()` skip values they already sent.
  - Process rows show or hide only when a rank appears or disappears.
  - A steady tick now sends only what changed: thread values, the total and the history paths. Before, it also resent 5 process group bangs, 10 process options, the hidden state text and the visibility bangs.
- **Idle Thread slots skip the meter pass (CPU-04).** The 320 slot meters start at `UpdateDivider=-1`.
  - Binding a slot sets the divider to 1 and forces one update of its group. That update also applies the V/T text `Sensors.lua` kept writing while the slot was idle. Unbinding sets -1 again.
  - With 12 threads, 260 hidden meters no longer update every tick.
  - Never ship the `CoreMeters.inc` half without the `CPU.lua` half. A -1 meter ignores `!SetOption` until forced, so the rows would freeze.
- **History graph (CPU-03, items 1-3).**

  - Both history meters dropped `DynamicVariables`.

## UsageMonitor registration by include (2026-10-23)

Phase B package B2 of the [performance review](../PERFORMANCE-REVIEW.md), theme T4 (findings CPU-05, ENGINE-04, XMOD-07), branch `perf/B2-usagemonitor`.

**Why.** UsageMonitor 1.0.1 (Rainmeter 4.5.28) gives each counter category one process-wide reader that reads the whole category every 1000 ms. A measure registers its category in the plugin's `Reload`, which Rainmeter runs at load even for a `Disabled=1` measure, and only unloading the measure (or changing its `Category`) unregisters it. Hiding the process list only disabled the ten slots, so the Process reader kept running for CPU Meter.

**What changed.**

- The ten `MeasureCPUProcess` slots moved from `Measures.inc` to `ProcessMeasures1.inc`. `Measures.inc` includes `ProcessMeasures<CPUShowProcesses>.inc` at the same place (before the controller), and `ProcessMeasures0.inc` is comment-only. `CPU.ini` sets `CPUShowProcesses=1` before the user include, so an older `CPU.inc` keeps the list.
- CPU Settings now refreshes CPU Meter when the list is toggled, as it does for the two rates, so the include follows the choice. That restarts CPU history, which a live toggle did not; Process count and every other setting still apply without a refresh.
- `CPU.lua` checks at load whether the slots exist. If the list is shown without them (only possible when the variable changes without the refresh), it binds nothing, so no bang names an absent measure, and the state line reads `Refresh CPU Meter to load processes`.

**Expected effect.** None at the default (`CPUShowProcesses=1`): the same ten measures load in the same order. With the list hidden, CPU Meter no longer registers the Process category. The Process reader stops only if no other loaded measure names it; Memory Meter's process ranks do while Memory Meter is loaded with `RAMShowProcesses=1` (see [RAM](RAM.md#top-processes)). Measured gains are left to step 3; the verifier's estimate for CPU alone is small, because the reader is shared.

## Busy-time metric and wider value field (2026-10-18)

The header, Thread rows, bars and both graph modes now read `Processor Information\\% Processor Time` instead of `% Processor Utility`. Utility is busy time multiplied by the actual clock over the nominal clock, so it is not a 0–100 busy percentage. On this i7-8700 (3192 MHz nominal), one-second Get-Counter and .NET `CounterSample.Calculate` probes read Utility 134.4 against Time 100.0 with every thread pegged (Actual Frequency 4289 MHz), and roughly 1.2–1.5 times Time at light load. The 0–100 bars and graph therefore filled once the CPU was about 74–85% busy, depending on the clock. A capture of the live skin under load showed the header at `134.4%` and every Thread cell clipped to `134.4…` in its 42-pixel field.
