# GPU module prototype

Implemented and restyled 2026-09-11. This is a bounded module prototype, not a release-readiness or performance result. Source changes are confined to GPU-owned paths; isolated preview evidence is generated under `build/`. No shared settings, styles, geometry, other modules, live Rainmeter configuration, installed dependencies or registry values were changed by this task.

## Main discrete GPU information

The inset displays the driver-reported name of the first discrete graphics adapter in Windows' high-performance ordering, without a separate heading. A one-time DXCore query enumerates D3D12 graphics adapters and explicitly checks `IsHardware=true` and `IsIntegrated=false`; vendor names and reported VRAM are not used as classification shortcuts. External discrete GPUs may rank ahead of internal ones. This identifies Windows' performance preference, not necessarily the adapter driving the monitor. [Microsoft enumeration and preference guide](https://learn.microsoft.com/en-us/windows/win32/dxcore/dxcore-enum-adapters), [adapter property definitions](https://learn.microsoft.com/en-us/windows/win32/api/dxcore_interface/ne-dxcore_interface-dxcoreadapterproperty)

The overview shows the detected card name followed by a combined memory/clock detail: `8192 MB GDDR5X @ 1607 MHz (1733.5 MHz)`. The value after `@` is base graphics clock; the parenthesized value is boost graphics clock. The detail wraps within a fixed two-line area, with the complete text and field meanings available in its tooltip. Physical capacity uses MB; the memory-chip manufacturer is available in the tooltip when exposed. No card-specific specifications or supplied screenshot values are saved or used as a lookup.

The original `AdapterInfo.cs.txt` is compiled and queried by the existing hidden Windows PowerShell helper once at load/refresh. DXCore selects the discrete adapter. For NVIDIA, the helper loads the installed driver API from Windows System32, matches its logical GPU to the selected DXCore LUID, and requires a unique physical GPU before reading physical framebuffer capacity, RAM type and RAM maker. Native resources and the NVAPI initialization are released after the query. There are no driver downloads, extra background processes or repeated metadata polling. Refresh after changing the graphics card; the next query describes the newly selected adapter.

RAM type and manufacturer use optional private NVAPI entry points whose scalar signatures/enums were reviewed against [NvAPIWrapper's API declarations](https://github.com/falahati/NvAPIWrapper/blob/master/NvAPIWrapper/Native/Delegates/GPU.cs). These are not supported across every driver. Missing entry points, failed queries, unknown enum values or an ambiguous physical-GPU match leave the affected fields unknown. Public identity and physical-framebuffer interfaces follow [NVIDIA NVAPI](https://github.com/NVIDIA/nvapi/blob/main/nvapi.h). No wrapper library is bundled.

Base and boost use the public [NvAPI_GPU_GetAllClockFrequencies API](https://docs.nvidia.com/nvapi/group__gpuclock.html), with the explicit BASE and BOOST selectors and graphics domain 0. Each reported kHz integer is converted to MHz with up to three decimals; the exact kHz values remain in the tooltip. Only a present, positive graphics value is accepted. Version 3 falls back to version 2 on an incompatible-structure result; version 1 is excluded because it cannot distinguish the requested clock type. Current frequency, memory frequency and observed maximum are never substituted. Each unsupported clock independently shows `-- MHz` with an unavailable tooltip. The separate live Clock row defaults to the current driver graphics clock and can use an explicitly selected HWiNFO override.

Replacing a card is handled at the next load or explicit refresh: the helper re-enumerates discrete GPUs and queries the selected adapter's identity again. Another supported NVIDIA card can provide all overview fields. Other vendors still provide DXCore name/dedicated memory, with unsupported memory technology and clock fields left unknown. No card profile is reused, and metadata does not continuously poll for hardware hot-plug events. Manual HWiNFO power and live-clock mappings remain explicit user selections; review and reselect them after changing hardware. Direct temperature binds to the newly selected adapter identity after refresh.

When physical capacity cannot be obtained, the second line uses the DXCore-reported dedicated memory in GiB and identifies that fallback in the tooltip; it is not rounded up to a nominal card specification. Memory technology remains `type unknown` if a supported driver interface does not expose it. AMD/Intel vendor-specific memory interfaces are not implemented in this iteration; their detected name/dedicated capacity remain available through DXCore, while memory type may be unknown. Individual failures preserve other known fields. The helper no longer creates a Direct3D device or queries feature levels, shaders, ray tracing or driver versions.

`No discrete GPU found` means no compatible discrete candidate was exposed. `Multiple discrete GPUs` means more than one candidate exists but performance sorting is unsupported. `GPU name unavailable` covers missing DXCore, unsupported properties, query failures, stale enumeration and process/compilation failures. Integrated/software adapters are never substituted. This initial path requires DXCore (Windows 10 build 18936 or later) and D3D12 graphics enumeration support; legacy adapters may not be exposed. Refresh after hardware changes. Long names clip within the inset; the complete name is in the tooltip. The activity percentage still spans **all GPUs**, as its visible scope states.

The header and first process bar reuse the same activity measure. Four additional measures select ranks 2-5 from Rainmeter's built-in UsageMonitor GPU category:

```ini
Alias=GPU
Index=1
PIDToName=0
Rollup=0
Percent=0
RawValue=0
```

Each rank selects one exposed **single process / adapter / engine instance**. The five bars use a fixed 0-100% scale and identify the process by executable basename plus engine type, with PID fallback; long labels retain their complete counter identity in the tooltip. One PID may occupy several rows for different engines or adapters. This does not add engines, identify the busiest adapter, or represent whole-adapter utilization. A process using one engine at 30% and another at 20% supplies two separate candidates. Two processes sharing one engine are not aggregated into an adapter figure. Microsoft describes a different aggregation for Task Manager's whole-adapter total. [Microsoft GPU telemetry semantics](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/)

`ProcessGraph.lua` validates the raw PID / adapter / engine identity and finite percentage before painting each bar. Invalid, out-of-range, missing and idle observations show `--` with an unavailable explanation and no colored bar; they never become fabricated zero readings. Blank engine types remain valid and display only the executable name or fallback PID. The script clears a previously visible bar when its rank becomes unavailable, and avoids meter writes/redraws when nothing changes. All five ranks share UsageMonitor's existing category worker; they add no polling process, new provider or saved history. Bars describe the currently ranked instances, not a time-series or five guaranteed-distinct processes.

Raw identity is intentional: name translation can merge multiple engine instances with the same executable name. `Rollup=0` alone does not prevent that. The script requires PID, adapter LUID and engine identity before showing a percentage. A blank engine type is permitted; it shows the executable name or fallback PID alone. The complete raw identity is available in the tooltip. Some Rainmeter 4.5 UsageMonitor cache paths can also share translated names with another skin; the identity guard suppresses those results instead of treating them as a peak engine. This was checked against the exact installed version's source. [Official UsageMonitor 4.5.26.3894 implementation](https://github.com/rainmeter/rainmeter/blob/v4.5.26.3894/Plugins/PluginUsageMonitor/UsageMonitor.cs#L359)

### Process-name lookup

The existing telemetry helper resolves only the up to five unique PIDs currently requested by the ranked graph. It uses Windows `OpenProcess` with limited query and synchronization access, `QueryFullProcessImageNameW`, and process names with the final executable extension omitted (for example, `chrome`). The graph sends a sorted canonical PID list through its Lua string return. The controller includes that list and a request generation in the existing five-second lease write; it validates the echoed generation, PID membership, UTF-8, bounds and session freshness before passing the map back through its own string return. Initial lookup or changing ranks can take a lease interval plus a telemetry sample. No new process, file, dependency installation or polling cadence is added.

At most five handles are retained. Dropped PIDs release their handles before replacements open; an exited, denied or failed lookup stays unavailable while that PID remains continuously requested. This avoids reopening a PID after detecting its previous process exited. Processes with identical executable names remain separate, and a PID can still appear for several engines. Each row's percentage and bar come from its original raw counter; name lookup is display-only and never enables UsageMonitor's aggregating name translation.

The map carries no full executable path. Names are bounded to 128 UTF-8 bytes, validated, sanitized for Rainmeter display and kept in tooltips when clipped. Failed, stale or missing name results immediately restore PID labels without removing usable percentages. Windows names describe the currently observed process; UsageMonitor exposes neither counter timestamps nor process creation identity, so this cannot certify that a retained counter belongs to the process lifetime observed by the lookup. The tooltip retains that age limitation. These controls do not prove hotplug or long-duration performance behavior.


At zero, a ranked UsageMonitor instance has no name. The panel shows `--` and **Idle / unavailable**, covering startup, genuine inactivity, unsupported drivers and missing counters without inventing a zero reading. Unexpected identities show **Unsupported counter format**. Collection failures may retain an earlier observation; UsageMonitor does not expose a timestamp here. No stale detector is claimed. Windows 10 Fall Creators Update or later and a suitable GPU driver are required by this counter family. [UsageMonitor options and limitations](https://github.com/rainmeter/rainmeter-docs/blob/master/source/manual/plugins/usagemonitor.html)

The **GPU memory** section reports dedicated framebuffer occupancy as `VRAM: used / total GiB`, with a matching occupancy bar. The underlying quantity is physical framebuffer bytes minus currently available dedicated bytes, so it includes memory the driver reserves as well as current allocations. The tooltip distinguishes total physical, allocatable, currently available and memory outside the allocatable framebuffer. It does not attribute those bytes to processes, D3D, video or bus functions. Zero availability is valid; zero allocatable capacity is unavailable rather than a false 100% reading. Capacities must be coherent exact integers within Lua's safe range.

The installed NVIDIA driver supplies [GetMemoryInfoEx](https://docs.nvidia.com/nvapi/group__driverapi.html) byte fields through the 80-byte version-1 structure. An unavailable or incompatible Ex interface can fall back to legacy version-3 `GetMemoryInfo`, converting its KiB values to bytes. No reported shared-memory ceiling is used as current usage. The separate **Shared RAM** row reads DXCore `MemoryUsage` for the shared segment of the selected adapter's sole physical node, displaying `resident` bytes and keeping `committed` bytes in its tooltip. These are independent accounting values; resident can exceed committed. Shared residency is system RAM, not additional physical VRAM. DXCore's calling-process `MemoryBudget` is not used for a system-wide total. [Microsoft memory query input](https://learn.microsoft.com/en-us/windows/win32/api/dxcore_interface/ns-dxcore_interface-dxcorememoryqueryinput), [memory usage fields](https://learn.microsoft.com/en-us/windows/win32/api/dxcore_interface/ns-dxcore_interface-dxcorememoryusage).

The **GPU activity** section reads four present domains from NVIDIA `GetDynamicPstatesInfoEx`: GPU, framebuffer/memory controller, video engine and bus interface. Each percentage describes busy time over the preceding one-second interval. They are independent activity measurements, not portions of memory capacity, and are never added. Valid zero displays `0%`; an absent domain displays `--`. Video is the driver's combined video domain; this interface does not supply separate encoder/decoder values. Bus is busy time, not bytes per second. The GPU domain is not relabeled as a Windows D3D counter. [NVIDIA dynamic P-state declarations](https://github.com/NVIDIA/nvapi/blob/main/nvapi.h), [Windows GPU engine semantics](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/).

Temperature, dedicated memory, shared memory, activity, power and current clock have independent direct statuses. Unsupported temperature therefore does not suppress other available fields, and DXCore shared RAM can work without NVIDIA interfaces. A device-identity change, invalid common header, stale sample or failed host clears all direct readings. Individual unsupported fields retain an explicit unavailable state with a reason; no zero or stored card specification is substituted. Explicitly selected HWiNFO overrides retain their separate identity and unknown-age semantics. Other-vendor dedicated-memory usage and activity providers are not implemented.

The existing `Temperature.lua` / `DriverTemperature.cs.txt` filenames remain for compatibility. The same helper now publishes a bounded 27-field `GPU_TEMP|4` record. Its first 21 fields retain the token, sequence, epoch, temperature status/value, LUID, hex-encoded name, dedicated-memory status/physical/allocatable/available, shared status/committed/resident, and activity status/GPU/controller/video/bus. Fields 22–25 append power status, power in mW, current-clock status and graphics frequency in kHz. Fields 26–27 append the validated process-name request ID and a bounded map of PIDs to hex-encoded executable basenames (or `?`). Numeric unknowns use `?`; session bootstrap remains version 1. Power/clock add two source preferences but no polling process, session file, hardware profile or new sampling cadence. All direct readouts refresh from the selected adapter after an explicit GPU refresh; the process-engine table retains its separate all-adapter scope.

## Direct GPU temperature

Temperature is read directly from the installed NVIDIA driver, independently of `GPUEnableSensors` and HWiNFO. `AdapterInfo.cs.txt` supplies the selected DXCore LUID to `Temperature.lua`; the original `DriverTemperature.cs.txt` source opens that exact discrete adapter and matches its NVAPI logical and physical identity. It accepts exactly one GPU-target sensor from the public [NVIDIA thermal interface](https://docs.nvidia.com/nvapi/group__gputhermal.html). It does not select an arbitrary NVIDIA card or substitute an integrated adapter. Unsupported vendors and driver interfaces display **Unsupported**; failures display **Unavailable**.

GPU Temperature is the regular graphics-chip reading. Hotspot describes the hottest measured area inside that chip and is different from VRAM temperature. This public interface exposed one regular GPU sensor on the tested card and no separate hotspot sensor; the panel does not invent one. The [HWiNFO author's explanation](https://hwinfo.com/forum/threads/hwinfo-gpu-section-what-is-gpu-hot-spot-temperature-max-measuring-differently-compared-to-gpu-hot-spot-temperature.10770/) provides further context.

One short bootstrap creates a random session identity, then RunCommand owns one persistent hidden PowerShell host. The host compiles the bundled C# source once, retains its native driver handles, and polls every `Max(1000,MetricsInterval,SensorInterval)` milliseconds, capped at 30000. It launches no process per sample. The bounded atomic snapshot includes the memory/activity/power/clock fields described above alongside the session token, LUID, sequence, timestamp, temperature status and signed integer Celsius value. Lua rejects mismatches, invalid values, sequence/time rollback and stale samples. Hardware/topology changes invalidate the old identity and require refresh; the helper never silently switches cards.

The temporary session uses `Parallax-GPU-<random token>.dat`, `.lease` and `.tmp` beneath Windows' temp directory. Lua validates the returned path against that exact directory and filename. It renews a bounded lease every five seconds or the next skin update. The helper stops when its retained Rainmeter parent exits or its lease expires (at least 15 seconds, or three sampling intervals). Normal skin close/refresh stops the owned host and removes its session files. These runtime files contain no settings and are not distributed. Startup and terminal errors do not trigger a process launch loop. Forced system termination can leave bounded temp files; no history or accumulating telemetry log is written.

Direct access removes the GPU temperature dependency on HWiNFO, but is not a measured CPU-cost improvement. Reading an export that HWiNFO already maintains is cheap; the direct path adds a host, polling and file exchange. Removing HWiNFO entirely might reduce total overhead, but a fair comparison requires equal sensor scope and cadence. No comparative benchmark is claimed.

## Per-application dedicated memory

Each of the five bottom process-engine entries shows a `VRAM:` value below its activity bar. This value is Windows dedicated GPU memory attributed to that process on that row's adapter/physical node. The top ranking remains activity-based and still spans all exposed GPUs. Several engines from the same process/adapter repeat the same memory value; two processes with identical executable names remain distinct. The bar and percentage still represent the individual engine's busy time, not a VRAM fraction.

Five built-in UsageMonitor measures use `Alias=VRAM`, mapping to `GPU Process Memory / Dedicated Usage`, with `Index=0`, `PIDToName=0`, `Rollup=0`, `Percent=0` and `RawValue=1`. A row binds only to a validated raw `pid_<PID>_luid_<high>_<low>_phys_<node>` prefix taken from its engine identity. No executable name is used for lookup. Changed bindings refresh before consumption; invalid or idle rows clear their reading and disable the lookup. Positive exact integer bytes within Lua's safe range format as MiB/GiB, with `<1 MiB` for small nonzero values.

UsageMonitor's named lookup synthesizes the requested name with zero when a counter is absent. Therefore zero cannot distinguish a real empty allocation from missing, starting or unsupported data, and the row displays `VRAM: --` for that ambiguous result. A positive observation still has no exposed timestamp; worker failures or PID reuse can leave retained counter data whose age or historical process identity cannot be certified. Exact PID/LUID/node matching prevents substituting another row or adapter, but does not add a freshness guarantee. The name lookup remains a separate display annotation. [Exact Rainmeter UsageMonitor implementation](https://github.com/rainmeter/rainmeter/blob/v4.5.26.3894/Plugins/PluginUsageMonitor/UsageMonitor.cs)

This is dedicated memory, separate from the `Shared RAM` system-memory reading above. On an integrated adapter, dedicated memory may itself be firmware-reserved system RAM. Windows includes resources shared across processes in each process's attribution; summing rows can therefore double-count allocations. These values are not an additive partition, do not reconcile to the main discrete GPU's total, and are not a sum of private bytes. [Microsoft process and GPU memory accounting](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/) Microsoft also documents per-process Dedicated Usage overreporting on affected Windows 10 systems; displaying a provider counter does not independently verify physical allocation accounting. [Microsoft counter limitation](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/gpu-process-memory-counters-report-wrong-value)

A function-based VRAM partition into 3D, video and textures is not implemented. The inspected NVAPI/DXCore interfaces provide framebuffer/segment accounting, not disjoint function totals. Video inputs themselves use texture resources, so those suggested categories can overlap. The total VRAM bar remains intact; no busy-time percentage or unclassified difference is relabeled as function-owned bytes. Application captures or ETW profiling are separate integrations, not installed dependencies. [NVIDIA memory fields](https://docs.nvidia.com/nvapi/structNV__GPU__MEMORY__INFO__EX__V1.html), [Microsoft process-memory input](https://learn.microsoft.com/en-us/windows/win32/api/dxcore_interface/ns-dxcore_interface-dxcoreprocessmemoryqueryinput), [video input resource requirements](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11videodevice-createvideoprocessorinputview)

The layout uses a 50-logical-pixel row pitch: name/percentage, the immediately adjacent activity bar, then dedicated-memory text. Its minimum is 650 logical pixels; larger saved heights remain honored and old saved heights are not rewritten at load. GPU Settings retains its independent 648px layout, and explicit Fit now saves 650. The additional five measures share one in-process category worker; no driver helper, temporary session, v4 protocol, per-sample process or dependency installation was added. Disabling named consumers does not promise worker suspension while the category still has consumers. This is a process-count/cadence description, not a resource-cost benchmark.

Proposed shared architecture/appearance/dependency update for integration: preserve the total VRAM bar; add non-additive per-row dedicated-memory observations through built-in UsageMonitor exact PID/LUID/node lookups, with zero/missing ambiguity and unknown-age limits. ## Cadence, files and persistence

The skin uses `MetricsInterval` (default 1000 ms). All nine optional registry measures start with `Disabled=1`.
