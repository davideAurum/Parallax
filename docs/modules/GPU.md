# GPU module prototype

Implemented and restyled 2026-09-11; layout revised 2026-10-10 into the CPU/Memory-style GPU Meter described in the first section after Dependencies. This is a bounded module prototype, not a release-readiness or performance result. Source changes are confined to GPU-owned paths; isolated preview evidence is generated under `build/`. No shared settings, styles, geometry, other modules, live Rainmeter configuration, installed dependencies or registry values were changed by this task.

## Layout revision 2026-10-10: CPU/Memory-style GPU Meter

User direction, 2026-10-10: condense and reorganize the GPU panel so it reads like CPU Meter and Memory Meter, and make the headline figure the real GPU load. The production sources (`GPU.ini`, `DriverMeters.inc`, `ProcessMeters.inc`, `GraphMeters.inc`, `Measures.inc`, `TemperatureMeasures.inc`, `GPU.lua`, `ProcessGraph.lua`, `Temperature.lua`, `Settings.lua`, `SettingsMeters.inc` and `User/GPU.inc`) are the reference for this section. Measures, plugins, helper sources, session files and sampling cadence did not change, so the Dependencies table above still applies; both Columns values remain supported.

**Headline is the driver's GPU load.** The title is now `GPU Meter`. The title-row value (`MeterActivityValue`) shows the NVIDIA driver's GPU-domain busy time (NVAPI dynamic P-state `GPU` domain, the Engine table's Core row), written by `Temperature.lua`; it no longer shows the UsageMonitor busiest process-engine figure. When the direct driver reading is unavailable or unsupported it shows `--`, with no fallback to the Windows counters. The History graph traces the same figure: `Temperature.lua` returns the Core percentage as its Script measure's number (0 while unavailable), and `MeasureGPUUtilizationHistory` (moved from `Measures.inc` to `TemperatureMeasures.inc`, directly after the controller; `Formula=MeasureGPUTemperatureController`, `MinValue=0`, `MaxValue=100`) feeds the Line meter. `MeasureGPUActivity` (UsageMonitor `Index=1`) now feeds only row 1 of the process table.

**Logical-pixel map.** Y is measured below the panel origin before `Scale`; `extra = Max(0, DataBarThickness-6)` is the same shift Memory Meter applies below its bars.

| Y | Element |
| --- | --- |
| 15 (center) | Title row: Lucide GPU icon, `GPU Meter`, driver GPU % at the right (hover swaps it for the gear). |
| 26-60 | Adapter inset, 34 px (was 64): line 1 the detected name (`MeterAdapterName`, Y 28); line 2 in Accent 1 (`MeterAdapterDetails`, Y 44, formerly `MeterVRAMValue`): `<size> <type> @ <base>-<boost> MHz`, e.g. `8.6 GB GDDR5X @ 1607-1734 MHz`. |
| 68 / 84 / 100 | `Temp:` / `Power:` / `Clock:` rows at 16 px pitch: 50 px labels, values in Accent 2 (`StyleValue` at body size, weight 600) right-aligned at the content edge, the CPU Meter Clock:/Fan: convention. |
| 124 / 140 | `Engine` header with the Lucide gauge glyph over the percentage column; header underline (`StyleTableHeaderRule`). |
| 144 / 160 / 176 / 192 | Core / Memory / Video / Bus rows: 52 px label, Shape bar at `ContentX+56` with width `ContentWidth-102`, centered vertically in its 16 px row so 1-12 px bars never touch neighbours, and a centered percentage in a 42 px column. |
| 210 | Engine footer divider (`StyleRule`). |
| 218 | `VRAM:` label with a right-aligned `occupied/total` reading; its full-width bar at `218+Max(20,23-DataBarThickness/2)` (238 at the default 6 px). |
| 250+extra | `Shared:` row with the Windows shared-residency amount; no bar. |
| 276+extra / 292+extra | Process table header (`Process`, Lucide gpu glyph, Lucide gauge) and underline. |
| 296+extra to 360+extra | Five 16 px process rows: name (`ContentWidth-112`), VRAM centered in 58 px, GPU % centered in 46 px. |
| 378+extra | Process footer divider. |
| 386+extra / 406+extra | `History` header with `0 - 100%` at the right, then the graph (`GraphHeight`, default 48). |

Natural height is `414 + GraphHeight + extra`, 462 logical px at defaults; the previous layout was a fixed 650 minimum with roughly 40 px unused below the graph. The monitor has 61 explicit meters (15 in `GPU.ini`, 21 in `DriverMeters.inc`, 20 in `ProcessMeters.inc`, 5 in `GraphMeters.inc`); `DynamicWindowSize` stays 0.

**Byte units.** User direction, 2026-10-10: byte units are decimal everywhere, as in Memory Meter and Disk Meter; the initial binary/Task-Manager-style labels of this revision were converted the same day. 1 KB = 1,000 bytes, 1 MB = 1,000,000, 1 GB = 1,000,000,000 and 1 TB = 1,000,000,000,000. The adapter inset and the `VRAM:` row print one decimal; the `Shared:` row and the process VRAM column print `%.0f MB`, `%.2f GB` or `%.2f TB`, the process column stepping by 1000 from `%.0f B` and `%.0f KB`. Tooltips say `decimal GB` / `decimal units` rather than `binary GB`.

**Adapter inset.** Base and boost clocks display as whole MHz (`1607-1734 MHz`, changed 2026-10-10 so the decimal details line fits the inset at the default width and body size); the exact kHz values stay in the tooltip. Size is decimal GB with one decimal (`GPU.lua` `capacity`: `%.1f GB` from 1,000,000,000 bytes, `%.0f MB` below): the tested card's 8589803520-byte physical framebuffer reads `8.6 GB GDDR5X`; the DXCore dedicated fallback of 8450473984 bytes reads `8.5 GB`; 536870912 bytes would read `537 MB`. An unknown type reads `(type unknown)`; missing clocks read `@ 1607 MHz base`, `@ 1733.5 MHz boost` or `@ -- MHz`; an unusable capacity still reads `VRAM unknown ...`. Exact bytes, kHz, memory vendor, the `decimal GB` note and the DEDICATED fallback note stay in the tooltip. Long values clip with an ellipsis at narrow widths; the tooltip carries the full text.

**Engine table.** It replaces the four stacked full-width 32 px label/value/bar blocks. Semantics are unchanged: independent NVAPI busy-time domains that are never summed. `Core` is the GPU domain (the header figure), `Memory` the framebuffer/memory controller, `Video` the combined video engine and `Bus` the bus interface.

**Memory rows.** `VRAM:` reads `%.1f/%.1f GB` of occupied/total (decimal, 1 GB = 1,000,000,000 bytes; `TB` with a 1,000,000,000,000 divisor when the total is at least 1 TB), e.g. `2.1/8.6 GB` for the suite fixture's 8589934592-byte total with 6442450944 bytes available, `0.0/8.6 GB` at zero use and `8.6/8.6 GB` when nothing is available; `--` when unavailable. Its tooltip states `(decimal units, 1 GB = 1,000,000,000 bytes)`. `Shared:` reads `%.0f MB`, `%.2f GB` or `%.2f TB` (decimal: 182452224 bytes read `182 MB`, 0 reads `0 MB`, 2147483648 reads `2.15 GB`) and has no bar because no honest ceiling exists for shared residency. The meters are `MeterGPUVRAMLabel`/`Value`/`Bar` and `MeterGPUSharedLabel`/`Value`, replacing `MeterGPUVRAMUsage` and `MeterGPUSharedMemory`, whose texts were `VRAM: 2.66 / 8.00 GiB` and `Shared RAM: 133 MiB` (pre-revision binary strings).

**Process table.** The duplicate `Top GPU processes` heading and its rule are gone; one CPU-style column header row remains. Rows are 16 px at body font size (previously 24 px at body minus 1). Grouping by PID, Windows basenames with PID fallback and `No active GPU process data` in row 1 when nothing is ranked are unchanged. This revision briefly added a capacity guard in `ProcessGraph.lua` that withheld per-process readings above the selected adapter's capacity (PID 1744, dwm, had been displaying `1.63 TB`, later `1.79 TB`, on an 8.6 GB card). The guard was dropped at merge in favour of reading `Local Usage` instead of `Dedicated Usage`; see "Local Usage instead of Dedicated Usage (2026-10-10)". The column formats positive bytes in decimal steps of 1000 (`ProcessGraph.lua` `formatBytes`: `%.0f B` below 1000, `%.0f KB` below 1,000,000, `%.0f MB` below 1,000,000,000, `%.2f GB` below 1,000,000,000,000, else `%.2f TB`): 228454400 bytes read `228 MB`, 4235264 read `4 MB`, 1073741824 read `1.07 GB`.

**History.** The `GPU utilization` heading and its rule are gone. Uncollected-cover behaviour is unchanged; while the driver reading is unavailable the trace reads 0%, as its tooltip states.

**Height and the 650 migration.** `GPU.ini` defines `GPUNaturalHeight=(414+#GraphHeight#+#GPUBarExtra#)` and `PanelHeightPx=(Round(Max(#PanelHeight#*(1-(#PanelHeight#=650)),#GPUNaturalHeight#)*#Scale#))`. Larger saved `PanelHeight` values are still honored, but a saved 650 (the previous Fit value and the previous shipped default, so present in every existing `User/GPU.inc`) is treated as Fit rather than as 188 px of dead space. `User/GPU.inc` now ships `PanelHeight=462`; GPU Settings `Fit panel height` saves 462 (`Settings.lua` `fitHeight`, its tooltip and the `SettingsMeters.inc` tooltips were updated). The settings window itself is unchanged at 648 px with 61 meters.

**Removed meters.** `MeterVRAMValue`, `MeterActivityLabel`, `MeterRule`, `MeterGPUMemoryHeader`, `MeterGPUUtilizationHeader`, `MeterGPUVRAMUsage`, `MeterGPUSharedMemory`, the second `MeterGPUProcessHeading` header, `MeterGPUGraphHeading`, `MeterGPUGraphRule` and the per-row `MeterGPUProcessBar` meters named in older sections below.

**Rationale.** The headline is the driver's own GPU load rather than one process-engine's share; the four engines are demoted to a compact table because they explain that figure rather than lead it; the memory rows adopt the shared RAM:/PAGE: family style; the process table has one header instead of two; and the panel ends at its content instead of at a fixed minimum.

## Delivered behavior

Load `Parallax\GPU\GPU.ini` through Rainmeter when testing the suite. The dense black panel follows `docs/APPEARANCE.md` revision 2 and, since 2026-10-10, reads like CPU Meter and Memory Meter: the user-selected Lucide GPU icon, the `GPU Meter` title and the driver's GPU busy time in `GPUColor` share one header (the CPU-style gear replaces the value on hover); a 34 px bordered inset shows the detected card name over an Accent 1 details line such as `8.6 GB GDDR5X @ 1607-1734 MHz` (decimal GB, 1 GB = 1,000,000,000 bytes); `Temp:`/`Power:`/`Clock:` rows with Accent 2 values follow; an `Engine` table lists Core, Memory, Video and Bus with shared-thickness bars and centered percentages; `VRAM:` with its full-width bar and a bar-less `Shared:` row adopt Memory Meter's RAM:/PAGE: style and decimal byte units; one CPU-style `Process` / VRAM / GPU % header precedes five 16 px rows grouped by PID (executable basenames with PID fallback; the tooltip preserves the PID and complete counter identity); and a `History` header with `0 - 100%` sits over the graph tracing the same driver figure. Natural height is 462 logical px at defaults (`414 + GraphHeight + Max(0,DataBarThickness-6)`); larger saved heights remain effective and a saved 650 is treated as Fit. Shared `GPUColor`, `FontFace`, palette, border and geometry are inherited. The official [ModernGadgets preview](https://raw.githubusercontent.com/raiguard/ModernGadgets/master/Wiki/preview.png) and [stylesheet](https://github.com/raiguard/ModernGadgets/blob/master/Skins/ModernGadgets/%40Resources/StyleSheet.inc) were inspected only as visual references.

The VRAM bar and the four Engine bars inherit global `DataBarThickness`, default 6 logical pixels and adjustable from 1 to 12. The shared derived thickness rounds the scaled value to physical pixels with a one-pixel minimum. Track and fill use that same thickness and center; unavailable fills have zero stroke. Engine bars are centered in their 16 px rows and everything below the VRAM bar shifts by `Max(0,DataBarThickness-6)`, so the full supported thickness range fits without changing percentages, rank collection or update cadence. The process rows no longer carry bars. The natural height applies when older saved heights are smaller, without rewriting those preferences.

The monitor joins `Group=Parallax|ParallaxGPU`, uses the prescribed include order and transparent snap gutters, and retains all context actions. Its separate settings utility joins only `Parallax`, so GPU-specific refreshes leave settings open. Every actual meter declares its type; no styles create meters. The new model metadata is separate from existing activity collection and sensor-mapping validation.

### Process-name lookup

The existing telemetry helper resolves only the up to ten unique PIDs requested by the ranked graph: every currently ranked PID (at most five, one per row), then the most recently ranked other PIDs from the last 15 seconds in the remaining slots, so a row that drops in and out of the top five keeps its name. At least five such slots remain even when five distinct PIDs are ranked; only a sixth drop-out within 15 s pushes out the oldest recent PID, which then waits for a fresh reply if it returns. It uses Windows `OpenProcess` with limited query and synchronization access, `QueryFullProcessImageNameW`, and process names with the final executable extension omitted (for example, `chrome`). The graph sends a sorted canonical PID list through its Lua string return. The controller writes a changed list and a new request generation into the lease file at once (at most once per second) and otherwise renews the lease every five seconds. A failed change write burns its generation, and the next cycle always commits a fresh one, even if the ranking reverted; only a failed renewal ends the session. The helper's reply may echo an older generation: its whole map must still match that generation's committed request (the last 32 are kept), and a name is passed on only for a PID requested without a break since that generation, so names of PIDs that stay requested no longer blank when the list changes, while a PID that left and re-entered waits for a reply at or after its re-entry. That rule matters for listed (handle-free) names: nothing pins those PIDs between samples, so a reply from before a drop could otherwise name a process that has since exited and whose PID was reused. The helper only ever sees the latest lease, and a lease read that changed mid-read is discarded, so a reply can never pair one generation with another's PIDs. UTF-8, bounds and session freshness are validated as before. A newly ranked PID usually shows its name after one telemetry sample plus a skin update (about 2–3 s at the default cadence, occasionally 4 s). Names do not depend on the GPU driver, so they survive a driver identity change. No new process, file, dependency installation or polling cadence is added.

Process names also work when no single discrete GPU is selected. If the load-time adapter query yields anything other than one valid discrete-GPU identity (`NONE`, `AMBIGUOUS`, `UNAVAILABLE`, an unreadable or all-zero LUID, malformed output, or no answer within its deadline), the controller still starts the same one bootstrap and resident host, for names only, passing the reserved all-zero LUID. The helper then never constructs or opens a GPU driver and publishes every GPU field as `UNSUPPORTED`. Lua ignores those fields and keeps showing why no adapter was selected on temperature, VRAM, shared RAM, activity, power and clock, exactly as before. A session or reply for any other LUID is rejected. When only the LUID was unreadable, the overview can still name the GPU while every GPU field reports that no unambiguous identity is available. On such machines the hidden Windows PowerShell host now runs for the skin's lifetime, as it already did with a discrete GPU. If the host cannot start or stops, rows fall back to PIDs and the GPU fields keep the adapter reason.

At most ten handles are retained. Dropped PIDs release their handles before replacements open; an exited or failed lookup, or a denied PID absent from the process listing, stays unavailable while that PID remains continuously requested. This avoids reopening a PID after detecting its previous process exited. Processes with identical executable names remain separate rows. A PID ranked at several engines is one row at its busiest engine's percentage. That percentage comes from the engine's original raw counter; name lookup is display-only and never enables UsageMonitor's aggregating name translation.

A non-elevated Rainmeter cannot open dwm, csrss, System and other protected or SYSTEM processes at all, with any access mask, and dwm in particular is usually the busiest GPU process. For such a PID, and for one that opens but has no usable image name, the helper reads one handle-free process listing per sample through ntdll's documented `NtQuerySystemInformation`: `SystemBasicProcessInformation` on Windows 11 26100.4770 and later, otherwise `SystemProcessInformation`. Any handle stays open across that first listing so the PID cannot be reused in between. The identity the listing reports at first sight stands in for the retained handle: the per-boot `SequenceNumber` that Microsoft documents for detecting PID reuse, or the creation time read from the documented structure's reserved bytes on older builds. It is compared every sample, and a mismatch or disappearance leaves the PID unnamed while it remains requested, exactly like an exited handle. Because the identity is checked only when the helper samples, a listed name can lag an exit followed by reuse of the same PID by up to one helper interval (2 s by default, at most 30 s) while that PID stays requested; a retained handle has no such window because it pins the PID. Once a PID's identity is established, a failed listing withholds its name for that sample only; a failure at first sight records nothing and is retried as a fresh first sight on the next sample. The listing runs only while such a PID is requested, which in practice is every sample because dwm is almost always ranked. Measured on the development machine with about 435 processes, `SystemBasicProcessInformation` costs about 60–90 µs per sample with a 64 KB buffer. The older `SystemProcessInformation` costs about 3.5–5.8 ms per sample and keeps a buffer of about 1 MB, because it enumerates every thread; at the default 2 s helper cadence that is roughly 0.2–0.3% of one core. Class 5 is used only when Windows reports class 252 unsupported; a transient failure is retried rather than locking in the costlier class. Names are the listed image name without its extension, so the kernel's own processes read `System`, `Registry`, `Memory Compression` and `Secure System`. [NtQuerySystemInformation](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntquerysysteminformation)

The map carries no full executable path. Names are bounded to 128 UTF-8 bytes, validated, sanitized for Rainmeter display and kept in tooltips when clipped. Failed, stale or missing name results immediately restore PID labels without removing usable percentages. Windows names describe the currently observed process; UsageMonitor exposes neither counter timestamps nor process creation identity, so this cannot certify that a retained counter belongs to the process lifetime observed by the lookup. The tooltip retains that age limitation. These controls do not prove hotplug or long-duration performance behavior.


At zero, a ranked UsageMonitor instance has no name. With nothing ranked, row 1 reads `No active GPU process data`, covering startup, genuine inactivity, unsupported drivers and missing counters without inventing a zero reading; unexpected identities are rejected rather than shown. Collection failures may retain an earlier observation; UsageMonitor does not expose a timestamp here. No stale detector is claimed. Windows 10 Fall Creators Update or later and a suitable GPU driver are required by this counter family. [UsageMonitor options and limitations](https://github.com/rainmeter/rainmeter-docs/blob/master/source/manual/plugins/usagemonitor.html)

The GPU domain is not relabeled as a Windows D3D counter. Power/clock add two source preferences but no polling process, session file, hardware profile or new sampling cadence. ## Direct GPU temperature

Temperature is read directly from the installed NVIDIA driver, independently of `GPUEnableSensors` and HWiNFO. `AdapterInfo.cs.txt` supplies the selected DXCore LUID to `Temperature.lua`; the original `DriverTemperature.cs.txt` source opens that exact discrete adapter and matches its NVAPI logical and physical identity. It accepts exactly one GPU-target sensor from the public [NVIDIA thermal interface](https://docs.nvidia.com/nvapi/group__gputhermal.html). It does not select an arbitrary NVIDIA card or substitute an integrated adapter. Unsupported vendors and driver interfaces display **Unsupported**; failures display **Unavailable**.

GPU Temperature is the regular graphics-chip reading. Hotspot describes the hottest measured area inside that chip and is different from VRAM temperature. This public interface exposed one regular GPU sensor on the tested card and no separate hotspot sensor; the panel does not invent one. The [HWiNFO author's explanation](https://hwinfo.com/forum/threads/hwinfo-gpu-section-what-is-gpu-hot-spot-temperature-max-measuring-differently-compared-to-gpu-hot-spot-temperature.10770/) provides further context.

One short bootstrap creates a random session identity, then RunCommand owns one persistent hidden PowerShell host. Without one selected discrete GPU, the same bootstrap and host start in names-only mode (see [Process-name lookup](#process-name-lookup)), and the GPU fields keep their adapter-selection reason. The host compiles the bundled C# source once, retains its native driver handles, and polls every `Max(1000,MetricsInterval,SensorInterval)` milliseconds, capped at 30000. It launches no process per sample. The bounded atomic snapshot includes the memory/activity/power/clock fields described above alongside the session token, LUID, sequence, timestamp, temperature status and signed integer Celsius value. Lua rejects mismatches, invalid values, sequence/time rollback and stale samples. Hardware/topology changes invalidate the old identity and require refresh; the helper never silently switches cards.

The temporary session uses `Parallax-GPU-<random token>.dat`, `.lease` and `.tmp` beneath Windows' temp directory. Lua validates the returned path against that exact directory and filename. It renews a bounded lease every five seconds or the next skin update, and rewrites it at once (at most once per second) when the requested process list changes. The helper stops when its retained Rainmeter parent exits or its lease expires (at least 15 seconds, or three sampling intervals). Normal skin close/refresh stops the owned host and removes its session files. These runtime files contain no settings and are not distributed. Startup and terminal errors do not trigger a process launch loop. Forced system termination can leave bounded temp files; no history or accumulating telemetry log is written.

Direct access removes the GPU temperature dependency on HWiNFO, but is not a measured CPU-cost improvement. Reading an export that HWiNFO already maintains is cheap; the direct path adds a host, polling and file exchange. Removing HWiNFO entirely might reduce total overhead, but a fair comparison requires equal sensor scope and cadence. No comparative benchmark is claimed.

## Per-application dedicated memory

Each of the five process rows shows a VRAM value in the column under the Lucide gpu glyph, beside its GPU percentage. This value is Windows' GPU Process Memory Local Usage for that process on that row's adapter/physical node. The top ranking remains activity-based and still spans all exposed GPUs. A PID's several ranked engines are grouped into one row, so its memory value appears once; two processes with identical executable names remain distinct. The percentage represents the PID's busiest ranked engine's busy time, not a VRAM fraction.

Five built-in UsageMonitor measures set `Category=GPU Process Memory` and `Counter=Local Usage`, with no `Alias`, plus `Index=0`, `PIDToName=0`, `Rollup=0`, `Percent=0` and `RawValue=1`. UsageMonitor treats a measure without `Alias` as custom. `PIDToName=0` already disabled PID translation under the former `Alias=VRAM`, so only the counter read changed. A row binds only to a validated raw `pid_<PID>_luid_<high>_<low>_phys_<node>` prefix taken from its engine identity. No executable name is used for lookup. Changed bindings refresh before consumption; invalid or idle rows clear their reading and disable the lookup. Positive exact integer bytes within Lua's safe range format in decimal steps of 1000 (`%.0f B`, `%.0f KB`, `%.0f MB`, `%.2f GB`, `%.2f TB`; 1 KB = 1,000 bytes, 1 GB = 1,000,000,000): 999 bytes read `999 B`, 1000 read `1 KB`, 1048576 read `1 MB`, 228454400 read `228 MB`, 1073741824 read `1.07 GB` and 1792337280000 read `1.79 TB`. Until the 2026-10-10 conversion this column used binary steps with Task Manager naming.

UsageMonitor's named lookup synthesizes the requested name with zero when a counter is absent. Therefore zero cannot distinguish a real empty allocation from missing, starting or unsupported data, and the row's VRAM column displays `--` for that ambiguous result. A positive observation still has no exposed timestamp; worker failures or PID reuse can leave retained counter data whose age or historical process identity cannot be certified. Exact PID/LUID/node matching prevents substituting another row or adapter, but does not add a freshness guarantee. The name lookup remains a separate display annotation. [Exact Rainmeter UsageMonitor implementation](https://github.com/rainmeter/rainmeter/blob/v4.5.26.3894/Plugins/PluginUsageMonitor/UsageMonitor.cs)

This is the process's memory in the adapter's own local memory, separate from the `Shared:` system-memory reading above. On an integrated adapter, dedicated memory may itself be firmware-reserved system RAM. Windows includes resources shared across processes in each process's attribution; summing rows can therefore double-count allocations. These values are not an additive partition, do not reconcile to the main discrete GPU's total, and are not a sum of private bytes. [Microsoft process and GPU memory accounting](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/) Displaying a provider counter does not independently verify physical allocation accounting.

### Local Usage instead of Dedicated Usage (2026-10-10)

Until 2026-10-10 the rows read `Alias=VRAM`, which is `GPU Process Memory / Dedicated Usage`. A smoke run on a GTX 1080 with 8,589,803,520 physical bytes (`build/gpu-native-smoke-20261011T004100448Z-03f2d240`, in the `standardize-units-gib-gb` worktree) showed dwm.exe at 1,790,597,615,616 bytes, displayed as `1.79 TB`. That machine ran Windows 11 Home build 26300 and NVIDIA driver 32.0.15.8266, about six days after boot.

Only that one counter was implausible. For the same process and adapter, Windows reported 545-767 MiB of Local Usage and about 1.26 GiB of Total Committed. The adapter-wide Dedicated Usage was about 2.7 GB, and the kernel's local-segment commit limit was 8,450,473,984 bytes. For most other processes Dedicated Usage stayed below the same process's Total Committed (0.2-0.97x); for dwm it was 1,358x. Windows does not document that relationship (its counter help reads only "Dedicated memory used"), so it is an observation from this machine.

Controlled churn did not reproduce the overcount. Resizing, minimizing and restoring a GDI window, a layered window and an isolated Edge flip-model window each moved dwm's Dedicated Usage by exactly its Total Committed change. Windows' increments and decrements were correct; the error behaved as a constant offset carried for the process's lifetime. What introduced it is unknown. No sleep, resume or display-driver timeout recovery occurred since boot. Two `nvlddmkm` event 153 entries ("Error occurred on GPUID: 100") on 2026-10-04 and 2026-10-08 are unconfirmed candidates. Microsoft documents a related per-process overreporting issue on Windows 10, version 1709 and later. [Microsoft counter limitation](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/gpu-process-memory-counters-report-wrong-value)

It never matched Dedicated Usage, which read 1-17x higher for ordinary processes. Task Manager showed dwm at 760,740 K. The rows therefore read Local Usage, so a value can be checked against Task Manager. No capacity bound or clamp is applied; Local Usage was not seen exceeding the adapter.

- **One Windows build.** The Task Manager match was verified on Windows 11 build 26300 only. Microsoft's article lists Task Manager's Details column as affected on Windows 10, so older builds may have used the other figure.
- **Local memory, not total allocations.** Local Usage is inferred to be memory currently in the adapter's local segment; Windows' help text says only "Local memory used". It can be lower than everything a process has allocated.

## Cadence, files and persistence

The skin uses `MetricsInterval` (default 1000 ms). All nine optional registry measures start with `Disabled=1`. At initialization, `Temperature.lua` enables a field's four-measure bank only when that field's source and `GPUEnableSensors` are both the literal string `1`; the shared name-enumeration measure is enabled only if at least one bank is needed. Settings actions refresh GPU to apply source changes. Enabled registry measures use `Max(1,Ceil(SensorInterval/Max(1,MetricsInterval)))` as their divider: the requested interval rounds up to a whole skin update. The default is 2000 ms. HWiNFO controls its own acquisition cadence. UsageMonitor's shared GPU category worker continues at 1 Hz independently of these settings; unload GPU to remove this consumer, and unload every consumer to release the category. No repeated subprocess or shell polling is used; the GPU-name command is a one-time metadata query at load/refresh.

`GPU.lua`, `Temperature.lua` and `ProcessGraph.lua` interpret measures and update displayed text / tooltips when they change. `Temperature.lua` is the sole writer of Power, Clock and sensor-source status, selecting direct data or the explicit override, and since 2026-10-10 also of the header activity value, the Engine table and the VRAM/Shared rows; it returns the Core percentage as its number for `MeasureGPUUtilizationHistory`. `GPU.lua` writes only the adapter inset. This prevents competing controllers from overwriting each other. Provider strings are stripped of option-expression delimiters before use in display options. Nothing is executed from those strings. Direct telemetry uses the bounded temporary session described above; display options are scalar data, while host commands contain only fixed method names and validated hex/integer arguments. No history is saved. All user settings live in the preserved `[Variables]` file. Include `Parallax\@Resources\User\GPU.inc` in the package's Variables files list. Preserve changed values and empty strings during the actual package upgrade test.
