The RAM panel follows `docs/APPEARANCE.md` revision 2. The latest layout uses the **Memory Meter** title, grouped hardware descriptions, compact **RAM:** and **PAGE:** readings with independent usage bars, and a five-row **Process / RAM** table above the bottom history graph. Entrypoints are `Skins/Parallax/RAM/RAM.ini` and the independent utility `Skins/Parallax/RAM/Settings/Settings.ini`. Implementation ownership remains limited to RAM's skin directory, `@Resources/Modules/RAM/`, `@Resources/User/RAM.inc` and this report. Shared files and other utilities are owned separately.

Capacity sits immediately beside the manufacturer. Separate configurations start on separate lines, and long descriptions wrap within the inset. There is no extra MEMORY HARDWARE heading or separate Installed, Type, Rate, Devices or Format table.

Two compact rows replace the PHYSICAL RAM subtitle and separate Used, Available and Total readouts: **RAM: used/total GB**, followed by **PAGE: used/allocated GB**. PAGE reports only paging-file space in use and current allocated capacity, summed across all paging files. Both use the selected decimal GB/MB unit and precision; Available remains accessible in the RAM tooltip. Each reading has its own usage bar directly below it, with separate show/hide settings. The **Process / RAM** table follows, with outlined/gridded physical-RAM history at the bottom. The skin inherits the shared font, neutral palette, inside border and transparent snap gutters. `RAMColor` controls the icon, both bars and history.

Three native `PhysicalMemory` measures supply used, available and total bytes. The RAM-owned resident `PageFileHost.cs.txt` reader supplies PAGE using Windows `EnumPageFilesW`; the previous `SwapMemory` measures were removed. A self-referencing Calc measure counts history samples. `Update=#MetricsInterval#` controls native sampling and history cadence; PAGE samples at the same configured interval, clamped to 1–30 seconds. Measures, graph and startup cover use divider 1. Five bundled UsageMonitor measures supply process-memory ranks with their own sampling behavior, described below. Interval changes require refresh. Hiding history preserves window size and does not claim to stop sampling; unloading removes this skin's measures and stops its PAGE reader.

Hardware inventory uses Rainmeter's bundled `RunCommand` plugin and one hidden Windows PowerShell query per RAM refresh. PAGE uses two separate setup-time launches: a session bootstrap and one resident Windows PowerShell/.NET reader. The resident reader calls Windows directly without starting a process for every sample. Applying display settings reformats cached data. Explicit typed numeric entry opens the shared one-shot input helper; arrows and toggles launch no process. There is no installation, credential or persisted inventory; missing access is reported explicitly. Test-only scripts, fixtures and runtime output remain under RAM's Tests directory and are excluded from staging.

## Grouped hardware overview

`MemoryInfo.ps1.txt` issues one `Win32_PhysicalMemory` query selecting `Manufacturer`, `PartNumber`, `Capacity`, `SMBIOSMemoryType` and `ConfiguredClockSpeed`. It does not query memory arrays, slot counts or form factors. Each returned record contributes to a configuration group. Counts describe Windows records and can include soldered memory; they do not establish free upgrade slots, removable-module count, channel mode, active ECC or maximum supported capacity.

Groups use canonical manufacturer, **exact per-record capacity in bytes**, raw SMBIOS type code and raw configured rate. Grouping occurs before rounding, so different configurations remain separate even when their formatted capacities happen to match. Manufacturer aliases use explicit exact-name mappings, not arbitrary vendor substring matches. Unknown manufacturers are labeled honestly and their distinct raw identities are preserved for grouping. A group ends with `x 1 module` or `x N modules`. Missing capacity, type or rate remains unknown rather than being inferred from other fields.

Capacity uses the selected decimal GB/MB unit and precision, consistently with the live readings. It is each record's capacity, not the group's sum or OS-usable total. Tooltips retain exact per-record bytes, raw SMBIOS type, rate explanation and manufacturer provenance.

Configured rate comes from firmware, not a live clock sensor. Current SMBIOS defines it as transfer rate; older SMBIOS and Microsoft's WMI documentation use MHz terminology. The formatter handles it as follows:

- DDR4 values within 1 MT/s of a supported standard speed bin use that nominal bin divided by two, with one decimal place and visible **MHz nominal**. Samsung's timing table gives a 0.75 ns nominal clock period for DDR4-2666; `1000 / 0.75` yields **1333.3 MHz nominal**. This is inferred from standard timing, not fractional precision measured from the device or supplied by integer firmware data.
- Other recognized double-data-rate types/rates use half the reported rate, rounded for display with **~** and **MHz derived**. The tooltip calls this an approximate derivation, not a measured clock.
- Types whose clock relationship is not handled, including LPDDR5's separate clock domains, retain the configured value as **MT/s**. Unresolved rate sentinels show **rate unknown**.

Only manufacturer may use the documented fallback. When firmware supplies an opaque or recognized unknown maker label, a strict full-match SK Hynix HMA DDR4 part-family pattern can identify **SK Hynix** using the vendor-authored naming guide. This is a general family rule, not an exact profile for one computer. `PartNumber` is transient query input only: it is never emitted, displayed or saved. Capacity, type and rate remain queried numeric fields and are never inferred from the part number. Tooltips identify fallback-derived manufacturer text.

The provider emits `RAMINFO2|capacity,type,rate,source,UTF8hexmaker;...`, where source `0` means firmware manufacturer text and source `1` means the documented manufacturer fallback. Manufacturer transport is limited to 128 UTF-8 bytes. Overlong or invalid provider text becomes unknown without discarding its numeric record. `InfoModel.lua` validates protocol structure, numeric bounds, record count and UTF-8. It replaces controls and Rainmeter-sensitive delimiters before display, keeping manufacturer data literal. Source `1` is accepted only with the expected SK Hynix manufacturer. No serial number, part number, machine identifier or user data is emitted.

`Info.lua` observes cached command status until completion, then stops its periodic work after brief layout rechecks. The process timeout is 12 seconds. A separate 15-second view guard settles the overview to **Unavailable** on the next skin update if completion is not delivered. Malformed or unsupported inventory also shows Unavailable. Refresh retries; overview failure does not disturb live physical-memory readings.

## Live memory semantics and units

- **RAM numerator:** OS-usable total minus available physical RAM, in bytes, from native `PhysicalMemory`.
- **RAM denominator:** `PhysicalMemory` with `Total=1`, meaning physical RAM usable by Windows. Hardware reservations can make this lower than installed physical capacity.
- **Available in the RAM tooltip:** the retained `PhysicalMemory` measure with `InvertMeasure=1`, including reclaimable standby memory rather than only the Windows Free list. Separate native calls can introduce small instantaneous differences between used + available and total while memory changes.

**PAGE** displays actual paging-file space in use and current allocated capacity. `EnumPageFilesW` supplies `TotalInUse` and `TotalSize` in pages for each paging file. The provider sums each field across a complete successful enumeration and multiplies by the OS page size. This excludes physical RAM and system commit accounting; it never subtracts RAM from commit or infers capacity from a usage percentage. The denominator is current allocation, **not the configured maximum**. It can change when Windows grows a paging file. Tooltips describe the scope and preserve exact aggregate byte counts. [Windows enumeration](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-enumpagefilesw), [page-count fields](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-enum_page_file_information).

A successful enumeration with no callbacks displays **No paging file**. Zero usage with positive allocation is a valid numeric reading. Startup displays **Checking...**; a missing API displays **Unsupported**; failed, malformed, partial, out-of-order or stale samples display **Unavailable**. An ordinary query error may recover on the next valid sample. A stopped host or failed bootstrap requires refreshing Memory Meter. These states do not change the independent RAM, process or history readings.

`PageFile.lua` bootstraps a random 32-hex session and validates its returned path against the process TEMP/TMP directories. It creates an initial lease before starting the resident host. The host publishes at most 512 ASCII bytes to its own `.dat` file through an atomic `.tmp` replacement; a `.lease` file carries the session token and heartbeat. Filenames and per-file paths from Windows are neither read nor published. Frames carry token, sequence, UTC epoch, status, used bytes, allocated bytes and count. The collector accepts at most 512 callbacks, validates pointer-sized structures and quantities, and rejects totals beyond Lua's exact integer range. No partial enumeration is displayed.

The skin renews its lease every five seconds, or on the next slower skin update. The host exits when its retained Rainmeter ancestor handle signals, when its lease expires after `max(15, ceil(3 * interval / 1000))` seconds, or when RunCommand stops it. The controller tracks its own launches per measure. Before stopping a tracked helper it refreshes the plugin's cached value and sends Kill only for running status `0`. RunCommand's documented initial state is `-1`, but a not-yet-updated native measure can expose cached `0`; neither unlaunched state establishes ownership. Completion is `1`. Observed completion and stop clear tracking, making repeated stop actions harmless. The controller removes only its validated session siblings on close or terminal failure; the host also cleans up on orderly exit. Forced process termination can bypass host cleanup. Lua rejects samples older than `max(8, ceil(3 * interval / 1000) + 2)` seconds or more than five seconds in the future and rejects sequence/time regression. Settings changes reformat cached samples without reading files, starting commands or advancing history. Startup compilation cost and resident process overhead have not been profiled.

RAM remains the physical-memory reading. Cache, compressed-memory and hardware-reservation details remain deferred. Process rows are a separate private working-set view; they must not be summed or labeled as total physical RAM or PAGE usage.

The header percentage String uses `Percentual=1`. Percentage, RAM bar and Line remain bound to used physical RAM. Rainmeter supplies their physical 0-to-total range; Line `AutoScale=0` and `Scale=1` retain a fixed 100% ceiling. The independent PAGE bar binds to `MeasureRAMPageRatio`, an event-only Calc with explicit 0-to-1 range. `PageFile.Display()` sets it from validated cached paging-file used/allocated bytes, updating no provider or history measure. Zero usage with positive allocation shows an empty track. Missing, stale, unsupported, no-file and zero-allocation states hide the PAGE bar while retaining the explanatory PAGE text and reserved geometry. RAM's bar is unaffected.

Per-module capacity, both RAM values, both PAGE values and process-memory values divide bytes by exactly **1,000,000,000 for GB** or **1,000,000 for MB**. Native RAM Strings disable automatic scaling; PAGE, inventory and process formatters use the same divisors. Raw data remains bytes and precision changes only text. The unit suffix applies to both sides of each used/total pair. Percentage, bar and history normalization are unchanged. RAM tooltips use explicit section variables for raw bytes because Rainmeter's `%1` tooltip substitution imposes different formatting. PAGE tooltips use validated aggregate bytes; inventory tooltips supply exact bytes and the same formatted group description as the overview.

## Top processes

The table has **Process** and **RAM** column headers and sits above bottom history. It shows up to five descending memory ranks, with a name and selected GB/MB value on each row. It uses Rainmeter's bundled UsageMonitor plugin: `Alias=RAM`, `Index=1` through `5`, `Rollup=1`, `Percent=0`, and `Blacklist=_Total|Idle`. The alias selects Windows **Process / Working Set - Private**. Its numeric value is bytes; its string value is the counter-instance name.

Private working set is resident physical memory private to the process, excluding shared pages. It is not private bytes/commit, total working set or pagefile usage. `Rollup=1` aggregates process instances with the same name before ranking. These are therefore same-name groups, not PID rows; a name alone cannot identify one process. The table's values do not sum to the RAM numerator, which has a different system-wide scope.

The Process counter category uses a shared worker sampling every second independently of the skin's `Update`. Increasing `MetricsInterval` reduces display updates but does not throttle that worker. The implementation adds no shell/process launch per sample. The worker may also serve other loaded skins using the same category.

`Process.lua` and `ProcessModel.lua` format the current ranked data; `ProcessMeters.inc` draws it. Unit/precision changes redisplay cached rows without a hardware inventory query or history reset. Names are validated as UTF-8, limited to 1024 bytes and sanitized as literal text. Long names clip within their row and retain the full display name in tooltips. Positive values below the selected precision show a threshold such as **<0.1 GB**, rather than a false zero. Missing/invalid rows are skipped. When no usable ranks are available, the table shows **No process data**; an empty name can also represent a zero-valued rank. UsageMonitor supplies no per-sample freshness signal here, so the UI does not claim to distinguish startup, an empty result, stale data or a failed counter. Tooltips explain the metric, same-name aggregation, selected decimal units and unavailable-rank ambiguity.

## History and unavailable information

The native Line buffer stores one sample per horizontal pixel, newest at right. At width 200, one column and scale 1, it has 188 slots: nominal capacity is 188 seconds at a 1000 ms interval, with 187 intervals between oldest and newest samples. Width, scale and cadence change capacity. This is update-based history, not a timestamped recorder; scheduling delays and suspension affect wall time.

Rainmeter zero-fills the initial Line buffer. An opaque shape covers uncollected slots with a two-logical-pixel overlap to hide the antialiased startup transition. A self-referencing Calc count resets on refresh and reveals collected samples; the cover vanishes at capacity. Grid and border render above the cover so blank history retains guides. The first few samples can be covered by the conservative overlap.

History is not saved. Refresh, reload or geometry changes applied by refresh restart it. Avoid graph-only `!UpdateMeter` actions, including `!UpdateMeter *`, unless sample counting is coordinated; normal full updates keep them aligned. Cached overview reflow and Settings changes do not append graph samples.

The overview reports unavailable inventory explicitly. PAGE has the provider status and freshness checks described above. Native PhysicalMemory exposes no freshness/status display here, so this skin cannot independently detect stalled physical-RAM values or OS query failures. It invents no freshness timestamp for physical RAM.
